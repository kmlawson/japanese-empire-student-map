# Is panning slower when deeply zoomed in?

**Asked:** "I feel like it is slower to pan when I'm deeply zoomed in, even if
there is almost nothing visible on the screen. Is that unavoidable?"

**Measured answer: it is not slower. It is cheaper, at every level I can
measure, and the frame budget is never exceeded.** Nothing was changed; this is
the investigation.

## How it was measured

Headless Chrome, **CPU throttled 4×** (`Emulation.setCPUThrottlingRate`), a
1400×900 viewport at **device pixel ratio 2**, and the map at its heaviest —
December 1942 with the Administrative layer fetched and on. Each run zooms by
a fixed number of wheel steps, lets `syncFine` settle, then drives 40–60
synthetic `pointermove` events through a real drag and reads:

* the **synchronous** cost of the move handler itself,
* the **`requestAnimationFrame` callback** duration, wrapping `rAF` to time it,
* `LayoutDuration`, `RecalcStyleDuration` and `ScriptDuration` from CDP
  `Performance.getMetrics`, as deltas across the drag,
* every **long task**, through a `PerformanceObserver`,
* and how much geometry is actually inside the frame — paths whose bounding box
  intersects the viewBox, and the number of path commands in them.

| 0 | 2800 | 1393 | 211,173 | 11 ms | 40 ms | 15 ms | 1001 ms |
| 4 | 1218 | 1002 | 102,432 | 11 ms | 32 ms | 15 ms | 993 ms |

And on the 1930 map, per-event rather than per-drag:

| wheel | viewBox width | move handler, median / p90 | rAF callback, median / p90 |
|---:|---:|---:|---:|
| 0 | 2800 | 0.1 / 0.7 ms | 0 / 0.1 ms |
| 6 | 231 | 0.1 / 0.7 ms | 0 / 0.1 ms |
| 12 | 24.7 | 0.1 / 0.7 ms | 0 / 0.1 ms |
| 15 | 24.7 | 0.1 / 0.5 ms | 0 / 0.1 ms |

* **The work falls as you zoom in.** 211,173 path commands inside the frame at
  the opening view, 11,855 at sixteen wheel steps. Layout falls with it.
* **60 frames take about 1,000 ms at every depth** — 16.6 ms each, which is the
  `requestAnimationFrame` interval. The map is idle-waiting for the next frame,
  not missing it, even at 4× throttling.
* **No long task fired at any depth**, during a pan or in the second after one
  ended. The `syncFine` settle 220 ms after a pan stops did not register.
* **The pan tracks the pointer 1:1 at every zoom.** 200 px of pointer moves the
  ground 200 px at every level except the opening view, where it moves 95 px —
  because `clampView` has reached the edge of the map. If anything *feels*
  different, it is that the fully zoomed-out map refuses to keep going.

## What this does not measure, said plainly

* **Rasterising, on a real GPU.** These numbers are the main thread. Panning
  changes the SVG's `viewBox`, which invalidates the whole layer, so every
  frame re-rasters the visible area — and that cost is set by the size of the
  window, not by the zoom. It would not explain "worse when zoomed in", but it
  is the part I cannot see from here, and it is the one real lever if panning
  ever has to be faster: drag a pre-rastered layer with a CSS transform and
  snap the `viewBox` on release.
* **Safari.** Its SVG rasteriser is not Chrome's, particularly around
  `vector-effect: non-scaling-stroke`, which this map uses on every stroke.
* **A loaded annotation set.** New today: a polygon with a *blurred* edge
  carries an SVG filter, and a filter is re-evaluated on every paint at a cost
  set by its area in device pixels. Zoom into a blurred area until it fills a
  retina screen and that is genuinely expensive — the one thing on this map
  that gets dearer the further in you go. Worth knowing before it is reported
  as a mystery.

## What would settle it

The report is of a feel, and a feel is real evidence — but it does not match
any of the above, so something about the conditions differs. Three questions
would narrow it: **which browser**, **what was switched on** (Administrative,
Cities, the graticule, a loaded annotation set), and **whether it was after
loading annotations** rather than on a bare map. Failing that, the live page
can be instrumented to record its own frame times for a session and report the
worst, which turns the feel into a number.
