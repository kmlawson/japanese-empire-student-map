# The whole map, surveyed for performance

**Date:** 27 August 2026, against `0f659af` (v1.82).
**Method:** the code read end to end with the hot paths traced by hand, then
four fresh measurements at HEAD — headless Chrome, CPU throttled 4× or 6×,
CDP `Profiler` at 100 µs, long tasks through a `PerformanceObserver`. Where a
number below is not marked fresh, it is quoted from the 25 August sweep
(`2026.08.25-performance-review.md`) and the code it measured has been checked
to be unchanged. Nothing in the repository was modified by this survey.

---

## How everything hangs together

Six scripts reach the reader; two more never do.

| file | raw | gzipped | when it arrives |
| --- | ---: | ---: | --- |
| index.html | 27,856 | 9,828 | first |
| styles.css | 78,591 | 25,237 | first |
| data.js | 615,720 | 184,198 | before the map |
| cities-gaz.js | 99,458 | 24,609 | before the map |
| map.js | 355,886 | 114,244 | before the map |
| relief.js | 1,681 | 634 | before the map |
| **japan-empire-map.svg** | **2,877,895** | **827,282** | before the map — **73% of the first paint** |
| annotate.js | 226,200 | 66,469 | on demand, pressing Create annotations |
| admin.js | — | — | on demand, alt-clicking Layers |

`data.js` and `cities-gaz.js` are generated tables — `JMAP.TERRITORIES`,
`EPOCH_OVERRIDES`, the gazetteer — and pure data: no work happens in them
beyond parse. `relief.js` is a tiny manifest for nine WebP sheets fetched only
when Topography is on. Everything that moves lives in `map.js`, and
`annotate.js` plugs into it through one deliberately narrow bridge:
`annHost()` hands the annotation module `project`/`unproject`, `clientToSvg`,
`svgEl`, `addScalable`/`dropScalables(idx)`, `rescaleAnn`, and a handful of
view calls, and takes back `tap`/`hover`/`grab`/`drag`/`drop`/`rescaled`.
Neither file reaches into the other beyond that.

The rendering pipeline, which is where every finding below lives:

* **A gesture** (wheel, drag, pinch) mutates `view` and calls
  `applyView()`. That writes the `viewBox` attribute — the browser pans and
  zooms the whole SVG for free — then schedules **one rAF** that does the real
  work: `rescale()` (rewrite the transform of every constant-size element:
  city dots, labels, hit targets — ~2,200 of them), `gateLabels()` (which
  names are candidates at this zoom; re-measures changed text), `placeLabels()`
  (greedy screen-space collision placement over every label), and
  `applyGazetteer()`. `rescale`/`gateLabels` run only when the zoom changed;
  `placeLabels` and `applyGazetteer` run on **every** frame of every gesture.
  220 ms after the last `applyView`, `syncFine()` considers grafting fine
  coastlines.
* **A hover** goes `onHover → pick → provinceAt → setHot/setHotProv →
  redrawHighlight → fillSlot → outlineOf`, plus `showTooltip`. `fillSlot` is
  keyed, so resting on one country is cheap; **crossing into a new one builds
  a masked outline from scratch** (a `getBBox` flush plus a mask and copied
  paths in `<defs>`).
* **A state change** (layer toggle, epoch, projection) goes through
  `applyState()`, which is deliberately total, and for a projection change
  through `reprojectDocument()`, which re-projects every path's `d` string.
* **Annotations** redraw per-feature since v1.82 (`redrawOne`), and their
  rescale walks only their own entries (`rescaleAnn`, v1.81).

The layering that keeps first paint sane: the administrative sheet (333 KB
gz), ROC provinces, fine coastlines, relief sheets, `annotate.js` and
`admin.js` are all deferred and confirmed absent from the first waterfall.
The one thing that is not deferrable today is the 827 KB base SVG.

## Fresh measurements at HEAD

**A. Hover sweep** — 60 moves diagonally across India → China → the Pacific,
CPU/6:

```
handler p50 0 ms   p90 8.5   max 15.2
long tasks: 147, 204, 54, 52, 110, 51, 71 ms
```

Resting is free; **crossing a frontier costs a long task** — up to 204 ms at
6×, so roughly 25–35 ms on this machine unthrottled, one to two dropped
frames per border on a mid-range laptop. This is the outline rebuild.

**B. 24 wheel steps**, CPU/4, profiled — top self time:

```
56.9%  (idle)
13.5%  getBoundingClientRect     <- uiBoxes, once per placeLabels per frame
 5.4%  getComputedTextLength     <- gateLabels re-measuring
 4.7%  setAttribute              <- rescale's ~2,200 transforms
 1.3%  placeScalable
 1.1%  placeLabels
```

Of the non-idle time, **forced layout reads are the biggest single item**, and
they are the same two reads the 25 August sweep blamed for the pinch running
at half frame rate on a phone (56% of its main thread). The mechanism is:
`rescale()` writes ~2,200 transforms, the document is now dirty, and
`uiBoxes()` immediately reads five `getBoundingClientRect`s plus an
`offsetParent` — each read a full layout of a 7,000-node SVG.

**C. Projection switches**, CPU/4, time to next painted frame / longest task:

```
-> albers      731 ms   [699]
-> laea        685 ms   [653]
-> mercator    179 ms   [150]
-> albers      620 ms   [588]      (second visit: no cheaper)
-> mercator    176 ms   [144]
```

Unchanged from the sweep, and the second visit to Albers costs the same as
the first — nothing is remembered. On a mid-range phone this is a two-to-four
second freeze.

**D. 40-step drag**, CPU/6: graticule off, wall 801 ms; on, 830 ms. The
graticule's per-frame label rewrite is real but small at this size — the
sweep's +120 ms was at a larger step count. Low priority now.

**Annotations** (fresh yesterday and today, CPU/4, dense 63-feature import):
a pointer move 20.6 → 3.7 ms across v1.81–82; selecting 28.2 → 3.4; a
keystroke 26.4 → ~0. The 25 August finding #5 is closed.

## Proposed improvements, ranked

### P1. Cache `uiBoxes()` per layout generation — the one fix that reaches every gesture

**Evidence:** 13.5% of wheel-zoom self time fresh (B above); 1,994 ms of a
6,109 ms pinch in the sweep, through the same line.

`placeLabels()` opens with `uiBoxes()` (map.js:2999) on every rAF of every
gesture, and the rects it reads — legend, zoom controls, info card, quiz
panel — change only when a panel opens, closes, folds or the window resizes.
`bumpLayout()`/`layoutGen` (map.js:2316) already exists and is bumped in
exactly those places, because `containerSize()` is already cached against it.

**Sketch:** memoise the boxes:

```js
var uiBoxCache = null, uiBoxGen = -1;
function uiBoxes() {
  if (uiBoxCache && uiBoxGen === layoutGen) return uiBoxCache.map(copy);
  ...existing body...
  uiBoxCache = boxes; uiBoxGen = layoutGen;
  return boxes.map(copy);
}
```

The copy matters: `placeLabels` pushes placed label boxes into the same
array. Return a shallow copy per call (or have `placeLabels` keep its own
array seeded from the cache). Audit that every panel open/close/fold path
bumps `layoutGen` — the info card and quiz box are the ones to check, and a
`ResizeObserver` on the four panels is a belt-and-braces way to make the
invalidation airtight rather than a list of call sites.

**Expected:** the pinch's 56% forced layout mostly gone (the sweep's
prototype measured −87% forced layout, p50 32.5 → 17.4 ms — 60 fps); a
measurable slice off every wheel frame. **Risk:** stale boxes if a panel
moves without bumping — visible only as a label placed under a panel.

### P2. `pinchState()` should not read `getScreenCTM` per move

**Evidence:** 1,158 ms of the sweep's pinch, `clientToSvg <- pinchState`.
Still in the code (map.js:3756).

`clientToSvg` exists because the SVG's CTM is authoritative — but during a
pinch the CTM is exactly what the gesture itself is writing, and the drag
path already converts client→map with arithmetic from the container rect and
`view`. **Sketch:** capture the container rect and `view` once in
`pinchStart`, and convert `mid` with the same arithmetic the pan uses
(`view.x + (cx - rect.left) * view.w / rect.width`). The existing
`onPointerMove` already fetches `container.getBoundingClientRect()` for the
pinch branch — one read is fine; it is the second, CTM-flavoured one that
forces layout after the viewBox write. **Expected:** the remaining third of
the pinch's forced layout. **Risk:** none if the arithmetic matches
`clientToSvg` — assert equality in a test at three zooms before switching.

### P3. Remember each projection's `d` strings — a second visit should cost what Mercator costs

**Evidence:** fresh table C — 620–731 ms freeze, identical on revisit;
`mercator` restores in ~177 ms because `el.__d0` holds the original string.

`reprojectDocument()` (map.js:1144) re-parses and re-densifies every path
from `__d0` on every visit to a non-Mercator projection. The shape of the fix
is already in the file: cache per mode —

```js
var key = '__d_' + projMode;                    // __d_albers, __d_laea
if (el[key] === undefined) el[key] = projMode === 'mercator'
  ? el.__d0 : moveD(el.__d0);
el.setAttribute('d', el[key]);
```

Invalidation: a graft (fine coastlines, admin sheet) arrives already
projected for the current mode via `reprojectGraft` — new nodes simply have
no cache and pay once. `refitEdgeClips` and the frame are per-mode already.
Memory: the paths are ~2.7 MB of the SVG's text; two extra copies ≈ +5–6 MB
retained on a reader who visits all three projections. Acceptable on
desktop; if it worries, cache only the most recent non-Mercator mode.

**Expected:** revisit cost 620 → ~60–90 ms at 4× (a `setAttribute` loop).
The *first* visit still costs what it costs — pair the cache with the busy
cursor the admin sheet already uses, or chunk `moveD` over two rAFs.
**Risk:** stale cache if `__d0` is ever rewritten — it is not today; the
fine-coastline path replaces nodes, which clears their expandos with them.

### P4. An outline cache for the hover path — crossing a border should not cost a long task

**Evidence:** fresh table A — 50–204 ms long tasks at 6× while sweeping;
sweep finding #4 (hover p90 33 ms, worse than dragging).

Two layers to it:

1. **`fillSlot` keeps only the current outline.** Moving A → B → A rebuilds
   A's mask from scratch. Keep a small LRU keyed by the existing `slotKey`
   (which already encodes the exact element set and `hiGen`): on `dropSlot`,
   detach the group and defs into the cache instead of discarding; on
   `fillSlot`, reattach on hit. Cap at ~8 entries and clear on `bumpHi()`,
   epoch change and projection change (all already funnel through
   `clearHighlight`/`hiGen`). The mask ids are unique (`mask-` + seq) so
   reattachment cannot collide.
2. **`litFor` runs `$$('[data-lit-for=…]')` over the whole SVG and scans
   `territories()` per call** — and it is called four times per hover change
   (unlight, light, twice in `redrawHighlight`). Build both lookups once per
   epoch in `composeEpoch()`: `litForIndex[id] = [els]`, `withinIndex[id] =
   [ids]`. Both inputs change only when the epoch is recomposed.

**Expected:** border-crossing cost drops to a class toggle plus a cache hit —
the 204 ms task becomes single-digit; first visit to each country unchanged.
**Risk:** a stale cached outline after a geometry change — `hiGen` is
already in the key precisely for this; the cache must include it.

### P5. `gateLabels()` should know when nothing it decides has changed

**Evidence:** 5.4% `getComputedTextLength` in the fresh wheel profile, plus
the `textContent`/display writes that feed it.

`gateLabels` runs on every zoomed frame and re-derives every label's text
and visibility. Its inputs are coarse: `labelLevel()` (a step function of
zoom), `featureLevel()`, `islandQuota()`'s bucket, epoch, language, layer
switches, provSource and the two names toggles. **Sketch:** compute a
signature string of those; if unchanged since the last run, skip the whole
walk (placeLabels still runs — positions do change). The quota's bucket is
already quantised (`quotaAt`), so a pinch that stays inside one band skips
everything, and crossing a band pays once.
**Expected:** most zoomed frames lose the label walk and all re-measures;
worth a few ms per frame at 4× with the admin sheet in. **Risk:** a input
missed from the signature shows as a label that fails to appear until the
next band change — enumerate the inputs from `labelVisible` and `mapLabel`
directly, and add a `names.js`-style check that flips each toggle and asserts
the labels move.

### P6. `placeGratLabels` — skip when the view is unchanged, write anchors once

Small and certain (fresh: +29 ms per 40-step drag at 6×; sweep: +120 ms).
The reuse of `<text>` nodes is already there; the remaining churn is one
`text-anchor` and one `transform` write per label per frame. Track the last
`view` signature; return early when identical. Write `text-anchor` only when
it differs (it never does after creation — meridian labels are always
`middle`, parallels `start`).

### P7. `placeLabels` micro-costs

Not urgent, but cheap: hoist `browseVisible()` out of the loop (it is called
per browse label); guard `L.el.style.display` writes behind a comparison
(most frames change nothing, and every write dirties style); reuse the
`free()` closure rather than allocating it per label per frame. Measured
weight today: ~1% each at 4×. Do them when the file is next open.

### P8. What is deliberately left alone

* **`drop()` after an annotation drag** — one full redraw + synchronous
  store (~24 ms dense at 4×), once per gesture, at the moment of release.
  It is the honest resync point; leave it.
* **Desktop pan and touch drag** — p50 at vsync in every fresh and swept
  measurement. There is nothing to fix.
* **`applyGazetteer` per frame** — 6–8 ms per whole drag over ~890 entries;
  a display-string compare per entry would shave it, but it is not what any
  reader feels.
* **`data.js` parse** — one-time, off the critical path after first paint.

### P9. The base SVG is 73% of first paint — a project, not a patch

827 KB gzipped; 6.3 s to a map on a 1.6 Mbps phone (sweep, table 3).
Options in rising order of effort: **brotli** precompression where the host
allows it (`.svg.br` ≈ 25–30% smaller than gzip for path text); coordinate
rounding in the build (the paths carry more precision than a screen ever
shows — measure the vertex-survival rule against a 0.01-unit quantise);
splitting the seldom-hovered backing/seam layers into a deferred fetch the
way admin already works. Each needs its own measurement pass; none belongs
inside a code fix above.

## Bug fixes

### B1. Editing on top of a shared link can still lose the reader's work — two confirmed paths

Priority above everything else in this report, by the project's own rule
(losing work is the worst thing the annotations can do). Both paths verified
in today's code by reading `store()`/`restore()`/`fromUrl()`/`backToMine()`
(annotate.js:204–265, 4203–4260).

* **(a)** Edits made while a shared set is open are stored under
  `ANN_STORE_SHARED` — but `restore()` and `offerRestore()` read only
  `ANN_STORE`. A student who unlocks a classmate's link, works for an hour,
  and closes the tab is never offered that work again on a plain visit; and
  reopening the *same link* runs `loadText`, whose `changed()` **overwrites
  the shared key with the link's original payload**. The work is gone.
* **(b)** `backToMine()` says "The shared set is in Undo if you want it."
  Pressing Undo pops the shared set into `feats` with `fromLink` now false,
  so `changed(true) → store()` writes the shared set **over the reader's own
  key** — and `shadowed` was already cleared. Closing the tab then loses
  their own set.

**Sketch:** (b) is small and clean — snapshot entries carry the storage
context: `snapshot()` stores `{f, s, link: fromLink}` and `undo()` restores
`fromLink = was.link` before `changed()`. (a) needs two pieces: `store()`
records a `dirty` flag in the stored object; `fromUrl` refuses to clobber a
dirty `ANN_STORE_SHARED` (offer it instead: "You changed this shared set
last time — keep those changes or load the link fresh?"), and
`offerRestore()` on a plain visit also checks the shared key and offers
dirty work found there. Both fixes are testable headlessly end to end, and
run12/run13 (the link scripts) are where the checks belong.

### B2. Selecting a mark inherits invisible style settings from the previous one

`syncFields()` (annotate.js:2724 on) writes each style control only when the
selected feature *has* the property — `if (hd && p['jem-arrow-head'])` — so
selecting a mark that lacks one leaves the control holding the previous
mark's value, and the next `styleChanged()` (which reads every control
unconditionally via `styleNow()`) stamps that stale value into the newly
selected feature. Change one thing about Arrow B and it silently gains
Arrow A's head, bend, symbol or fill opacity. This is also the best
candidate yet for the user report that style stickiness "remembered the
first thing I made" — the panel genuinely does carry old values across
selections. **Fix:** in `syncFields`, set every control to the feature's
value *or its default* — the defaults are already named in `props()`. One
pass, ~ten lines, and a run-script check: style A heavily, select plain B,
nudge B's colour, assert B gained nothing else.

### B3. Distances, areas and label anchors are wrong across the antimeridian

`haversine`/`sphericalArea`/`anchorOf`/`midOf` (annotate.js:419–470, 1349)
take raw longitude differences. A line from +179° to −179° measures as
~358° of arc instead of 2°; a polygon over the Gilberts returns a planetary
area; `anchorOf` averages longitudes and puts the label at Greenwich. For a
map whose 1942 frame includes the Gilberts, Wake and the date line, a
teacher tracing the Pacific war will hit this. **Fix:** unwrap each ring
against its first vertex (`lon += 360` while `lon - prev > 180`, etc.)
before measuring or anchoring — measurement only; the stored coordinates
stay as entered.

### B4. Right-clicking an arrow's bend handle does nothing but summon the context menu

`rightClick` returns `removeVertex(i, 0, 2)`; for an arrow the ring has two
points, `v = 2` fails the bounds check, `false` bubbles out and the browser
menu opens over the map — the one place the file's own rule ("a right click
on a mark is unambiguous") is broken. The natural meaning is **straighten
the arrow**: delete `jem-curve`/`jem-curve-t`, `redrawOne(i)`, say
'Straightened.', return true. Three lines in `rightClick` before the
`removeVertex` call.

### B5. Verified non-bugs, so they are not re-reported next sweep

* The touch hold-timer "teleport" claim (earlier agy #6): `drop()` calls
  `letGo()` on every pointer-up, which clears the timer. Not reproducible in
  code or in run15's finger section.
* `parseWhen` reading "1931" as an end date: fixed — `upto` exists and the
  clock passes it.
* `beforeunload` after field edits: fixed — `fieldChanged`/`styleChanged`
  call `setDirty(true)`.

## Suggested order

**B1 first** — it is data loss, both paths are confirmed at HEAD, and the
fixes are small. Then **P1 + P2 together** (they are the same pinch, and P1
alone is most of it), then **B2** (it is almost certainly the reported
stickiness bug), then **P4** (hover is the map's most-used gesture), then
**P3** (the projection freeze, worst on phones), then **P5/P6/B3/B4** as a
batch of small certain wins, **P7** opportunistically, and **P9** as its own
project when payload next matters.
