# The annotation feature, audited

26 August 2026. A thorough pass over `annotate.js` — my own testing, plus
independent reviews from `codex` and `agy` through the ask-friends skill, both
given a context block saying what the feature is for and what matters about it.
Raw reviews are in `2026.08.26-annotation-audit-codex.md` (21 findings) and
`-agy.md` (12).

**Two reviewers this time, and that is worth stating** because the last round
had one. See *Why agy failed before* at the foot.

Nothing here is relayed unchecked. Everything below was either driven in a
headless browser until it happened or read carefully enough to say why it
cannot.

---

## What I fixed

### 1. Undo after a rename destroyed the whole set — CONFIRMED, measured

The worst thing this feature can do, and it took two presses to do it.

A title, description or date edit took **no undo snapshot**. So Undo did not
"fail to undo the rename" — it reached past the rename and consumed whichever
structural snapshot was underneath. Measured before the fix:

```
load two marks   ->  ['first', 'second']
rename the first ->  ['first RENAMED', 'second']
press Undo       ->  []                       <- the whole set is gone
press Undo again ->  "Nothing left to undo."
```

The snapshot it found was the state *before the file was loaded*. There is no
redo. Both reviewers found this independently (codex 8, agy 3).

Fixed by snapshotting in `fieldChanged` and `styleChanged` — but **one snapshot
per burst of typing, not one per keystroke**, or a sentence would take forty
presses to undo and would fill the forty-deep stack with one field. The first
change in a burst takes the snapshot; the rest ride on it; the burst ends after
900 ms of quiet or when the selection changes.

### 2. An edit after saving left the page willing to close silently — CONFIRMED, measured

`changed()` defined "unsaved" as `feats.length > 0`, which is a different
question from "does this differ from the file I saved". Two consequences, both
measured: editing a title after a save did not re-arm the unload warning, and
deleting the last mark *cleared* it. Also found by both (codex 3, agy 4).

Fixed. `changed()` sets dirty outright, and because `fieldChanged` and
`styleChanged` do their own drawing rather than going through `changed()`, they
set it too — which is why the first attempt at this fix did not work and the
test caught it.

### 3. The clock read an end date as the *first* of January — CONFIRMED, measured

Mine, from yesterday. `parseWhen` filled in a missing month and day with 1, for
starts and ends alike. So a mark written **start 1931, end 1931** vanished the
moment the clock reached September 1931, and one written **start 1931-05-01,
end 1931** was never visible at all — its end landing four months before its
start. agy found it (8) and it reproduced first time.

Fixed: an end date now rounds up to the end of whatever precision was written —
"1931" ends on 31 December, "July 1937" on the 31st — with a real leap-year
rule for February.

That exposed a second wart, which is also fixed: a mark running through 1931
puts both 1 January and 31 December into the stage list, so the reader stepped
from a stage labelled "1931" to another labelled "1931". A stage nothing starts
at now reads **"end of 1931"**.

### 4. The clock was accidentally quadratic — CONFIRMED by reading, fixed

codex 11. `inScope()` called `stages()`, which walks every feature and sorts;
`redraw()` calls `inScope()` once per feature. So drawing was O(n²) in the
number of marks, and playback did it once a frame. The stage date is worked out
once per redraw now.

### 5. "Annotation features are not supported on small screens" — was not true

The panel docks to the foot of a phone, every tool works with a finger, and the
suite tests exactly that. The buttons were being *removed* below 700px. They
are offered at every width now, with one honest sentence instead: *"Annotating
works on a phone, but a desktop or a tablet is easier."*

## What I checked and could not reproduce

Reported by a reviewer, driven in a browser, did not happen. Recorded so nobody
spends the afternoon on them again.

* **"Back to my annotations then Undo overwrites the reader's own set."**
  codex's top finding and agy's second — the one place they agreed most
  emphatically. Driven end to end: own set stored, classmate's link opened,
  "Back to my 1 annotation" pressed, Undo pressed, page reloaded. The reader's
  own work was in storage throughout and came back intact on reload. What I did
  see is that the press did not appear to switch the visible set — worth a
  look, but it is not the destructive bug described.
* **"Work added on top of a shared link is lost on reload."** agy 1. Not
  reproduced in the same run.
* **"Right-clicking an arrow's bend handle deletes the whole arrow."** agy 7.
  The arrow survived; the mark count was 1 before and 1 after.
* **"A quick tap arms a drag that fires with no finger down and teleports the
  mark."** agy 6. Checked against the saved coordinates rather than the screen
  position, because a pan moves everything: `[120,25]` before, `[120,25]` after.

## What is real and still open

Verified or clearly true from the code, not fixed today, in the order I would
take them:

1. **Loading a file replaces unsaved work with no confirmation** (codex 2). The
   old set goes to the undo stack, but the reader is not asked and the unload
   warning is disarmed by the load.
2. **Failure of the only automatic backup is hidden** (codex 4). Every
   `localStorage` exception is swallowed. A student whose quota is full is told
   nothing and finds out when the tab dies.
3. **Unfinished lines and areas are discarded without confirmation** (codex 7):
   twenty polygon corners traced, then a stray tap on another tool, and the
   trace is gone with no undo.
4. **Async packing can publish a stale link while claiming success** (codex 6),
   because the staleness check is array identity and edits mutate in place.
5. **Two tabs silently overwrite each other's backup** (codex 5).
6. **Polygon holes are filled rather than cut, and counted as extra area**
   (codex 13); **GeometryCollections are drawn as polygons** (codex 12). The
   *saved file* is unaffected — round-tripped a hole and a GeometryCollection
   through save and both came back byte-correct — so this is a drawing and
   measurement fault, not a data-loss one.
7. **Antimeridian**: area and label placement are wrong across ±180° (agy 9).
8. **Copy link on a `file://` page produces a path, not a URL** (codex 14).
9. **Handles are drawn for MultiPolygon and MultiLineString rings that the drag
   and delete code cannot edit** (codex 21, agy earlier).

## What I checked that is fine

* **Round trip.** Five features in — polygon with a hole, MultiLineString,
  a dateline-crossing line, a point at nine decimal places, a
  GeometryCollection — five out, every geometry type preserved, every title and
  description intact, coordinates unrounded. Only the *link* quantises.
* **Scale.** 50, 200 and 500 marks: load 53/45/75 ms, and one keystroke in the
  title field costs 3/6/10 ms. Not a problem at any size a class will make.
* **The clock against editing.** The list keeps showing every mark while the
  clock filters the map, selecting a hidden mark works, and saving writes the
  whole set rather than what is on screen.

## Why agy failed before, and what changed

Last round agy returned one line: *"no output produced — a tool required the
'command' permission that headless mode cannot prompt for, so it was
auto-denied."* I reported that as agy being unable to open the file. **That was
the wrong explanation.** The skill already hands agy the whole file inline; it
does not need to open anything.

What actually happens: agy is *invited* to go and look. The prompt says "Review
the quality of this file: annotate.js" and asks for line numbers, and once in a
while it decides to open the file to do that properly. In headless mode any
tool it asks for is auto-denied, and it then produces nothing at all.

It is nondeterministic, which is why it worked today. Tested to rule out the
alternatives: the same 163 KB file inline works; the full rules block on a
small file works; running from the directory that actually contains
`annotate.js` works. None of those is the trigger.

Three changes to `ask-friends.sh`:

* agy is told in as many words that the file is inline, that it has no tools,
  and that it should count lines from the BEGIN marker.
* its stdin is `/dev/null`, as codex's already was.
* **the failure is detected.** If the permission complaint comes back the
  script asks once more, and if the result is still too short to be a review it
  appends a line saying so in terms that cannot be mistaken for findings. The
  real cost last time was not the missing review — it was that a one-reviewer
  round could be written up as though two reviewers had agreed.
