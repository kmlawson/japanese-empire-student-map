# The JavaScript and the tests, reviewed

**Date:** 9 September 2026, against `0dff576` (update 338).
**Method:** every `.js` file in the repository read for structure, then measured
with small scripts rather than eyeballed: comment share and gzipped size,
function lengths, layout-forcing DOM reads attributed to their enclosing
function, five-line duplicate windows within and across files, functions and
module variables defined and never referenced, and for the tests, every
`sleep()` literal, browser launch, page load and hand-rolled helper. The full
suite was run once (`node tools/test/all.js`) to get per-script seconds that
are measured today rather than remembered. Nothing in the repository was
modified except this file and the line the run appended to
`tools/test/runs.jsonl`.

Where a number below is an estimate rather than a measurement it says so.

---

## The short version

**The scripts.** `map.js` is 17,965 lines and 844 KB, of which 369 KB is
comment. It gzips to 272 KB and would gzip to 128 KB without the comments, so
every first-time reader downloads 144 KB of prose written for the next
editor. It has grown from 356 KB to 844 KB since the 27 August survey, 2.4× in
thirteen days, and it is now one 17,951-line closure holding 319 module
variables and 404 named functions. The code inside is sound: the layout-read
caching the August reviews asked for is in, `innerHTML` is used only to clear,
there is no `eval`, and the dead code amounts to four functions. The problems
are the shape of the file, not its lines.

**The tests.** 61 scripts, 18,539 lines, 2,112 checks. A full run averages
504 s over the 75 recorded in the last nine days, and the `changed` runs
meant to be the fast path average 324 s over 37, because an edit to `map.js`,
the file that changes hourly, selects 34 of the 61 scripts. About 13.8 hours
of wall-clock test time was spent in nine days. Inside the scripts there are
871 literal sleeps totalling 833 s on a single pass, 140 page loads waiting
on `networkidle0`, and 57 private copies of the same twenty-line harness.
The suite's own helpers (`settle.js`, `annotations/suite.js`) already solve
all three; they were written and not adopted.

If only four things are done:

1. **Strip comments from the shipped `map.js`** at build time. Halves the
   largest script's transfer size; changes no behaviour and no source.
2. **Finish adopting `ready()`** in the 33 test scripts still sleeping by
   number after a page load, and replace `networkidle0` with
   `domcontentloaded` plus `ready()`. Estimate: a full run under five minutes.
3. **Narrow `changed` for `map.js` by section**, using the 42 banner
   comments already in the file, so a label edit runs the label tests.
4. **One `tools/test/suite.js`**, deleting the 57 copies of `check`, 52 of
   the puppeteer resolver, 34 of the `matchMedia` shim and 28 of `open()`.

### 1.2 One closure, 319 variables, 42 sections

`map.js` is a single IIFE. Its banner comments already divide it into 42
sections, and several of them are the size of the modules that have been
split out:

| section | lines | note |
| --- | ---: | --- |
| the air routes (`map.js:9286`–`10963`) | ~1,700 | on-demand content; `air-play.js`, 676 lines, is *already* lazy |
| train tools (`map.js:2382`–`3811`) | ~1,400 | `trains.js` is lazy; its host-side half is not |
| the right-click menu (`map.js:11624`–`12670`) | ~1,050 | |
| legend, palette, choropleth, pies (`map.js:13036`–`15525`) | ~2,500 | |
| controls (`wireControls`, `map.js:16601`–`17556`) | 956 lines, 65 listeners, one function | |

The project has proved the split works: `annotate.js` plugs into `map.js`
through `annHost()` and a handful of hooks, and neither reaches into the
other. The air section is the obvious next candidate because it is the same
shape — its own data (`JMAP.AIR`), its own card, its own menu, its own
`airHost()` at `map.js:10815` — and because `air-play.js` was split out while
the 1,700 lines it depends on were not.

If splitting files is unwelcome, split the *source* and concatenate at build.
The stripping step above needs a build step anyway; concatenation is one
`cat`. What matters is that a reader of the air code opens a 1,700-line file
and not a 17,965-line one, and that `git diff` on a label change does not sit
beside a diff on the choropleth.

**Module state.** 319 `var`s at the top level of the closure, every one
reachable from every one of the 404 functions. `annotate.js` has 74 at its
level, `trains.js` 46. This is what makes the file hard to split, and it gets
harder with each week: the number is a coupling count. Nothing to fix in a
day, but every new feature that adds to it should be asked whether it could
own its state the way `airApi`, `trainApi` and `annApi` do.

### 1.3 Four script loaders

The same eleven lines — create a `<script>`, set `src` through `asset()`,
append, handle `onload`/`onerror` — appear four times, each with different
failure behaviour:

| site | loads | on failure |
| --- | --- | --- |
| `loadAdminPanel`, `map.js:1349` | admin.js | clears a pending flag |
| `fetchOne`, `map.js:2704` | trains.js and a timetable | sets `failed`, counts down |
| `loadAirPlay`, `map.js:10861` | air-play.js | clears `airPlayWanted`, resyncs the button |
| `loadAnnotate`, `map.js:17724` | annotate.js | queues callers, `alert()`s |

One `loadScript(name)` returning a memoised Promise would replace all four
and give the station files (§1.1) somewhere to go. The differing failure
behaviour is fine; it belongs in the callers, which is where a Promise puts
it.

### 1.4 The style tax

The five hand-written scripts are ES5 by syntax: 2,357 `var`s in `map.js`,
no `const`, no `let` to speak of, no arrow functions, and 403
`.forEach(function () {})` closures. But the same code depends on Pointer
Events, `Map` and `Set` (`pointers.size`), `Array.from`, `Math.hypot`,
`fetch`, `Promise`, `classList.toggle` with a force argument and
`non-scaling-stroke`. Every browser that runs the map already runs ES2015,
so the syntax buys nothing. What it costs:

* `var` is function-scoped, so a `var k` inside a loop in a 956-line function
  is the same `k` as one three hundred lines above it. `let`/`const` make
  that an error at parse time.
* `Array.prototype.slice.call(nodeList)` where `[...nodeList]` would do;
  `function (a, b) { return a - b; }` where `(a, b) => a - b` would do. Over
  11,600 code lines this is real reading cost.

Recommendation: allow ES2015 syntax from now on and stop converting new code
down. No rewrite — the old code works — but no new `var`.

### 1.7 The bitfield

`layerCode` (`map.js:4345`–`4529`) writes the link's `layers=` code with
literal integers — `8388608`, `2097152`, `16777216`, `4096`, `8192`,
`16384` — and its comments record **three separate occasions** on which two
settings were written to the same bit and a shared link silently flipped a
stranger's setting. The comments are the record; nothing in the code prevents
a fourth.

A table of named bits, `BITS = { mono: 1 << 21, world: 1 << 24, … }`, with a
five-line startup check that no two entries share a value, would have caught
all three at load time. `layers-url.js` now tests the pairs that collided
before, which guards the past and not the future.

### 1.8 Layout reads, after the August fixes

The caching the 25 and 27 August reviews asked for is in: `containerSize()`
and `uiBoxes()` are memoised on `layoutGen`, `pinchState` captures its
rectangle once at pinch start and the move handler reads nothing, and
`gateLabels` batches its `getComputedTextLength` calls behind a comment
explaining why. The per-frame path (`rescale`, `placeLabels`) forces no
layout that was not already deliberate.

What is left is on the **hover** path, which runs on every mouse move:

| function | reads |
| --- | --- |
| `pick` (6674), `nearestSubUnit` (6702), `stationDist` (6806) | `getBoundingClientRect` each |
| `placeTooltip` (7764) | `getBoundingClientRect` |
| `keepClear` (12650–12662) | `getScreenCTM`, `getBBox`, `getBoundingClientRect` |
| `reachable` (16449–16467) | three `getBoundingClientRect` and a `getScreenCTM` |

Several of these read the container's rectangle, which `containerSize()`
already holds. Whether the others force a layout depends on whether the
document is dirty when they run — after a `rescale` it is — so the honest
statement is that they are candidates, not measured costs. `compare_perf.js`
with `--admin` on a hover sweep would settle it in a minute.

### 1.9 Smaller things

* **`data.js` opens with `const JMAP = {}`**, a lexical global that shadows
  `window.JMAP` for every script after it. `relief.js`, `cities-gaz.js` and
  the station files therefore *must* load after it, and `index.html` carries a
  comment saying so. The generator should write `window.JMAP = window.JMAP ||
  {}` like every other generated file does, and the ordering hazard is gone.
* **`JEM_ASSETS` is written into `map.js` itself**, which means every build
  that touches any asset rewrites `map.js` and changes its hash, so a change
  to a relief tile invalidates the 272 KB script for every reader. A separate
  tiny `assets.js` (or a `<script>` block in the short-cached `index.html`)
  would leave `map.js` cacheable across releases that do not touch it.
* `tools/compare_perf.js` is good and is the only tool that can answer §1.8.
  It carries its own copy of the puppeteer resolver, the fifty-third.
* `'use strict'` is present in all five hand-written files. Good.
* `innerHTML` appears 22 times in `map.js` and every one is `= ''`. There is
  no `eval` or `new Function` anywhere. The link-security review of 25 August
  still stands.

### 2.2 Where the time goes

**1. Sleeping by number.** 871 `sleep(n)` literals across the scripts sum to
833 s on a single pass, and loops multiply some of them. The serial sum of the
`SECS` table is 2,388 s, so at least a third of all test time is a timer.
`settle.js` was written to end this — its header records "725 seconds of
literal sleep" at the time — and it is required by 24 of the 57 test scripts.
The other 33 still `goto` and then sleep 1,800–5,000 ms. The total has gone
*up* since the helper was written, from 725 s to 833 s, because new scripts
copied old ones.

The biggest single offenders, by literal sleep on one pass:

| script | sleeps | total | longest |
| --- | ---: | ---: | ---: |
| air.js | 61 | 60.7 s | 4,000 |
| airplay.js | 49 | 53.7 s | 3,000 |
| trains.js | 49 | 53.5 s | 3,200 |
| demography.js | 26 | 39.3 s | 5,000 |
| mapstrip.js | 19 | 31.1 s | 3,600 |
| population.js | 28 | 28.9 s | 3,200 |
| hanlabels.js | 22 | 27.0 s | 3,000 |
| layers-url.js | 20 | 24.6 s | 2,200 |
| keys.js | 31 | 22.0 s | 2,800 |

`settle.js` itself says which sleeps should stay: the ones waiting for a
transition. A sleep after a click that toggles a layer is waiting for
`applyState`, which is synchronous, plus one frame. `until(page, fn)` in the
same file expresses that in the page's own terms.

**2. `networkidle0`.** All 140 page loads wait for the network to be idle for
500 ms after the last request. That is a fixed half-second per load that
`ready()` then waits *again* to make sure of, on top of moving the SVG,
`data.js`, `map.js` and the station files — about 5 MB, uncompressed — from
Python's `http.server`. `waitUntil: 'domcontentloaded'` followed by `ready()`
is what the scripts actually need, and it is what `ready()` was written for.
Estimate: 146 loads × (0.5 s idle + most of a second of transfer) is two to
three minutes of serial time.

**3. The fast path is not fast.** `changed` picks groups from the changed
paths, and the file that changes most — `map.js`, 329 commits since 1 August —
maps to `core`, `points`, `links` and `data`:

| edit to | scripts | serial | at four |
| --- | ---: | ---: | ---: |
| everything | 61 | 2,388 s | ~600 s |
| map.js | 34 | 1,293 s | ~323 s |
| annotate.js | 34 | 1,036 s | ~259 s |
| data.js, texts/city-names.csv, build_texts.py | 30 | 1,070 s | ~268 s |
| texts/territories/*.csv | 26 | 987 s | ~247 s |
| index.html | 23 | 895 s | ~224 s |
| styles.css | 23 | 755 s | ~189 s |

`core` alone is 19 scripts and 672 s, and every product file maps to `core`.
The recorded `changed` mean of 324 s against the full mean of 504 s is the
same fact measured: the narrowing saves a third, on a file that changes eight
times a day.

`map.js` is not one thing and its 42 section banners already say what it is.
`git diff -U0 HEAD -- map.js` gives the changed line ranges; a table from
banner to group — the air section to `transport`, the legend and choropleth
to `data`, the labels to `core`, the controls to `core` and `links` — would
let a label edit run the label tests. The rule that anything unrecognised
runs everything still holds for a hunk that straddles sections or lands in
the shared state at the top. This is the highest-value change in the runner
because it is aimed at the file that is edited most.

**4. The long tail.** With four workers the run cannot end before its longest
script does, and today's longest were `layers-url` at 158 s and `stations` at
132 s. Both are long for reasons that are not the work: `layers-url` opens a
fresh page for nearly every case (15 `open()` calls, each a full load plus
900–1,600 ms of sleep) and `stations` hovers station by station with a sleep
per square. Neither needs a fresh page per case — the map's own `applyState`
and a `?layers=` navigation are what a reader would do — and neither needs a
sleep where `until()` would return on the first frame the label appears.

**5. Everything else is small.** 67 browser launches at roughly a second
each is one minute serial; Chrome's own startup is not where the time is.

### 2.3 What is unnecessary

**The harness, copied fifty-seven times.** Counted across the 61 scripts:

| copied thing | copies | already exists in |
| --- | ---: | --- |
| `check(name, cond, detail)` and the pass/fail counters | 57 | `annotations/suite.js` |
| the puppeteer resolver IIFE | 52 (+1 in compare_perf.js) | `annotations/suite.js` |
| the `matchMedia` SHIM | 34 | `annotations/suite.js` |
| an `open(browser, url)` helper | 28 | `annotations/suite.js` (`page`) |
| the `no page errors` check | 37 | — |
| `puppeteer.launch({...})` | 65, in **five** variants, `protocolTimeout` 120/150/180/240 s or unset | — |

`all.js` lists `suite` in `HELPERS` as though `tools/test/suite.js` existed.
It does not; only `annotations/suite.js` does. Writing the top-level one —
it can start as a re-export of the annotation one plus `settle.js` and
`downloads.js` — and deleting the copies removes an estimated 1,200–1,500
lines and makes the next fix to `open()` a fix in one place. The five launch
variants become one, with a single `protocolTimeout` that the retry logic in
`all.js` already assumes.

**Two runners.** `tools/test/annotations/all.js` is a copy of the top-level
`all.js` from before it learned groups and timings (16 shared five-line
windows). It lists `run` through `run14` and not `run15`, so it is already
wrong, and the annotations README describes `run` through `run11` only.
`node tools/test/all.js ann` does the job. Delete the copy, fix the README.

**Suites that are one suite in three copies.**

* `trains.js`, `krtrains.js`, `kftrains.js` share 23 and 16 duplicate
  windows and eight identical check names ("zoomed out: the layer is gone",
  "play moves the clock", "but the data stays in memory"…). They are one
  parametrised suite over `STATION_SYS`, which is exactly how `map.js` treats
  the three railways. One file, one browser, three configurations.
* `japanpop.js`, `manchupop.js`, `twpop1930.js` share four check names and
  ten windows — the "dataset is there / code is positive / same map again /
  switches on nothing else" preamble. Same remedy.
* `mono.js` and `theme.js` share 12 windows; `labuan.js`, `names.js` and
  `pin.js` share seven each.
* The annotation scripts `run6`–`run10` share 10–12 windows with each other:
  the open-panel-pick-tool-draw preamble, which `suite.js` provides as
  `openPanel`/`stickTool` and which they inline anyway.

**A script in four groups.** `hanlabels` (80–108 s) is in `core`, `data`,
`transport` and `links`, so it runs on nearly every edit. `names` and
`mapstrip` are in two. The `data` group is the one that makes sense for it;
the others are worth a sentence each in `GROUPS` saying why, or removal.

**The `SECS` table is hand-kept and stale again.** Sixteen of the 61 entries
are more than 30% off today's measurement. Overstated: `relief` 140 → 76 s,
`air` 159 → 109, `hanlabels` 108 → 80, `names` 62 → 32, `mono` 27 → 11,
`labuan` 22 → 10, `beta` 22 → 9, `zoom` 13 → 6. Understated, which is the
kind that hurts: `airplay` 78 → 123 s, `kftrains` 19 → 43, `run14` 32 → 42.
The runner sorts longest-first on these, so `airplay`, the third-longest
script, is scheduled as if it were the eleventh — which is the fault the
table's own comment records fixing once already. The runner *has* the per-script seconds in
`results` when it writes `runs.jsonl` and throws them away, recording only
the total. Write them, and read `SECS` from the last run that has them.
The same record would give a per-script flake rate, which is the number
nobody can currently compute: 23 of 75 full runs had a failure and nothing
says which script.

**`runs.jsonl` is tracked in git.** Every run dirties the tree. The `changed`
runner ignores `tools/test/`, so it is harmless there, but 116 lines of
timing history in the repository is not something anyone will read from a
commit. Either ignore it or accept the churn — say which.

### 2.4 What is worth keeping exactly as it is

* The `changed` runner's principle — unrecognised paths run everything, and
  the reasoning is printed — is right and should survive the section-level
  narrowing.
* The orphan check that refuses to run when a script is in no list. It has
  earned its place twice.
* The stillborn-retry logic and the buffered per-script output.
* `settle.js` and `downloads.js`: small, correct, and the model for the
  rest.
* `annotations/suite.js`'s `page()`: dialog handling, error capture, the
  shim, the settle — this is the `open()` every other script should be
  calling.
* The two-pointer discipline (mouse and finger driven separately) and the
  "press it, do not dispatch at it" rule in `air.js`. These catch real bugs
  and the cost is worth paying.

### 2.5 Recommendations, in order
