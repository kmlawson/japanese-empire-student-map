# Test suite review — 15 September 2026

Reviewer brief: the suite takes 8–10 minutes for 70 scripts (~2,450 checks), four
at a time. Wanted: (a) fewer/faster/better tests, (b) a more trustworthy way to
pick what to run before a minor fix. Both, with numbers.

## Method

- Parsed `tools/test/runs.jsonl` (189 runs) for per-script wall-clock: each line
  carries `scripts`, `checks`, `secs` and a `per` array of `{n, s, checks}`.
  Medians per script taken over every run that names the script.
- Read `tools/test/all.js` (622 lines): scheduler, `TRIGGERS`, `SECS`.
- Grepped all 70 scripts for the cost primitives: `sleep(`, `networkidle0`,
  `newPage()`, `goto(`, `setViewport`, `until(`.
- Timed selected scripts against my own server on port 8124 so as not to
  disturb another session on 8123.
- Cross-read `docs/tasks.md` for which tests are named as having caught
  something.

Findings are appended as they are established; nothing here is a plan for
work I have not done.

the only place in the sample where a sleep is load-bearing.

This is not a proposal to ship the cap. It is the measurement that says the
numbers in the sleeps are not doing work: they are margin, chosen on a slower
machine or in a busier run, and the right fix is `until()` on the condition
the sleep stands in for.

### One sleep, converted and measured

`tools/test/citytap.js:101` — `await flip(p, '#opt-train-tools', true); await
sleep(7000);` — replaced with `until(p, () => document.querySelectorAll(
'path.train-line').length > 0)`. **The condition was true in 41 ms.** The sleep
is seven seconds and the script runs it twice, once for the mouse and once for
the finger: 14 of `citytap`'s 39 seconds, for eight checks.

But converting the *next* sleep the same way failed, and the failure is the
lesson. `citytap.js:117` sleeps 8 s after a `goto`, and what it is waiting for
is not only that the track is drawn but that the map has written its `layers=`
code into the URL, which the script then reads at line 111. Waiting on
`path.train-line` alone let the script run ahead and read an incomplete code,
and the reloaded page then had no railway at all — a 40-second timeout where
there had been a passing test.

**So: the condition to wait on is the last observable side effect, not the
first.** A mechanical sleep-to-`until` sweep will break things. A sleep
converted with the condition the following line actually reads will not.

One more detail worth fixing while doing it: `until()` at `settle.js:60`
defaults to `polling: 'raf'`. Under four concurrent browsers a starved page
can stall its animation frames; `polling: 250` costs nothing and cannot.

**"a hundred seconds a script, and every check still passed"**. The suite went

built on timeouts, and the argument for `until()` being the only wait.

- *the connections layer* — `krtrains.js:115-136`, `mntrains.js:107-191`.

### The printed timetable page, opened four times

`trains.js:796-842`, `krtrains.js:269-295`, `kftrains.js:212-223`,
`mntrains.js:319-337`. Each opens the whole `deploy/timetable/…` page and
checks: N tables present, a machine-transcription warning before them, it opens
in English/characters, another script is a press away, no page errors. The
table count is per-file and worth keeping (14, 173, 132, 18). **The furniture —
the warning, the language switch, the page errors — is one contract in
`build_*_trains.py`'s shared template and should be one check, in `trains.js`,
over the four pages in a loop.** It is currently four page loads.

### `hanlabels` re-tests label gating and card headlines

`hanlabels.js:82-110` ("the map is labelled before the switch is touched",
"not one label went missing", "nothing came out blank") is the same gating
contract as `labels.js` and `labelcats.js`. `hanlabels.js:155-163` and
`:183-193` re-open a city card and a station card to assert the headline/second
line arrangement that `stations.js:232-241` and `names.js` already assert; what
is specific to `hanlabels` is only *that the characters displace the
romanisation*. The two extra page opens are `hanlabels.js:33`, which alone
accounts for 22.4 s of its 70 s.

### `no page errors` — 48 scripts assert it separately

Every script ends with its own `check('no page errors', …)` over its own
`p.__errs`. That is correct as a guard and wrong as a *check*: `suite.js:108`
already collects errors on `p.__errs` for every page it opens, so `report()`
could fail the script on any uncollected page error automatically and the 48
hand-written copies could go. It saves no time — it removes 60-odd lines and a
class of "I forgot to add the check to the new script" bug.

### Cheap scripts that duplicate expensive ones

`citytap.js` (8 checks, 39.4s, **4.92 s/check — the worst ratio in the suite**)
stages the Korean railway, the train tools and the gazetteer from scratch, twice
(mouse and finger), to assert that a tap on a city beats the line under it.
`trains.js` and `krtrains.js` both already have the tools up over Korea. Either
fold these eight checks into `krtrains.js` — which has the stage built and
costs 12.2s — or give `citytap` a `?layers=` code to open on instead of
building the state by clicking. Its 14 seconds of `sleep(7000)` measured 41 ms
as an `until()` (see §2).

## 6. Procedure

### `JOBS` is capped at 4 and the machine has 10 cores

`all.js:536-537`:

```js
const JOBS = Math.max(2, Math.min(4,
  parseInt(process.env.JOBS, 10) || Math.floor((os.cpus().length || 4) / 2)));
```

`JOBS=8` is silently clamped to 4. The comment above it argues that past four
"they queue on the machine rather than on each other, and a test that is
starved of CPU starts failing on timing rather than on truth." **On this machine
(`hw.ncpu` 10, Mac13,1) that is not what happens.** Measured with a scratch
runner that uses the same list and the same longest-first sort, against a server
on :8124, *while another session was running its own tests* (load average 14):

A fixed 16-script subset (295s serial), run five times alternating:

| jobs | wall | checks | failures |
|-----:|-----:|-------:|---------:|
| 4 | 83.0s | 522 | 0 |
| 8 | 49.3s | 522 | 0 |
| 4 | 83.0s | 522 | 0 |
| 8 | 49.5s | 522 | 0 |
| 6 | 54.1s | 522 | 0 |

And then the whole suite:

| run | jobs | wall | checks | failures |
|-----|-----:|-----:|-------:|---------:|
| the suite's own recent runs | 4 | 494–504s | 2,449–2,468 | 0–3 |
| **scratch runner, uncapped** | **8** | **264.2s** | **2,471** | **0** |

**Raising the cap from 4 to 8 halves the suite, changes no test, and produced
zero failures on a machine that was already busy.** The scripts are not CPU
bound — §2 shows them 88–94% asleep — so eight browsers idle together about as
well as four do.

Two honest caveats. The gain is bounded below by the longest script: with
`trains` at 151s, no number of jobs takes the suite under about 250s until
`trains` is split or its sleeps go. And the failure mode the comment warns
about is real in kind — the `protocolTimeout` no-verdicts in `runs.jsonl` are
that — so the retry at `all.js:566-583` must stay. I would raise the cap to 8
with `JOBS` still overridable downwards, not remove it.

Also: `--dry` divides by a hard-coded 4 (`all.js:522`, `Math.round(secs / 4)
+ 's at four at a time'`). If the cap moves, that line has to read `JOBS`.

### `all.js` does not start the server, and should

Its docstring (`all.js:4`) tells the reader to run `python3 -m http.server 8123
&` first, and `suite.js:78` already reads `MAP_URL`, so everything needed is in
place. This has cost a real session: `docs/tasks.md:19486` records "all 59
scripts failing to start in 28s, which was my own doing: `all.js` does not start
the static server … and a port cleanup earlier in the session had killed it."

It is about fifteen lines: bind a free port, `spawn('python3', ['-m',
'http.server', port], {cwd: root})`, poll `/deploy/index.html` for a 200, set
`process.env.MAP_URL`, kill it in `done()` and on `SIGINT`. A free port rather
than 8123 also removes the collision with another session in the same
checkout — which the project already warns about in `CLAUDE.md`, and which I
hit writing this report.

### Page reuse would buy almost nothing

Measured against :8124, three times:

```
launch 456ms  open1 571ms  open2 387ms  open3(bbox) 366ms  reload 26ms
launch 366ms  open1 457ms  open2 396ms  open3(bbox) 384ms  reload 21ms
launch 405ms  open1 466ms  open2 383ms  open3(bbox) 374ms  reload 21ms
```

A browser launch is ~0.4 s; a full map page — 73 KB of HTML pulling a 3.7 MB
SVG and a 1.1 MB `data.js` — opens in ~0.4 s. Seventy launches is 28 s and the
roughly 250 page opens across the suite are about 100 s: **under 7% of the
1,970 s serial total.** A shared browser, a page pool, or a `goto`-only-when-
the-URL-differs cache would save perhaps 30 s of serial time, at the cost of
cross-test state leakage — the thing a fresh page is for. **Not worth doing.**
The 4 MB is not the problem; `sleep(5000)` is.

The one figure that *is* worth acting on in that table is `reload 26ms` against
`open 400ms` — a script that re-opens the same URL repeatedly (`relief` opens
17 pages, `hanlabels` 11, `names` 12) could `goto` the same page instead of
making a new one, but that is tens of seconds, not hundreds.

## Postscript: the flaky scripts are not flaky alone

Ran each of the four most-suspected scripts five times, solo, against :8124 on
a machine that had quietened down:

```
sugar:    23/0  23/0  23/0  23/0  23/0
labels:   24/0  24/0  24/0  24/0  24/0
mapstrip: 47/0  47/0  47/0  47/0  47/0
keys:     34/0  34/0  34/0  34/0  34/0
```

Twenty runs, no failures. But earlier in this session, **`mapstrip` run the same
way while the machine was loaded gave 46 passed, 1 failed** — and the capped
run of it, seconds later, gave 47/0.

So the flakiness in `runs.jsonl` is contention-dependent, not intrinsic: these
scripts fail when a `sleep(N)` that was long enough on an idle machine is not
long enough on a busy one. That is the same defect as §2 from the other side,
and it changes two things above:

- **Recommendation 1 (`JOBS` 8) carries more risk than the zero-failure run
  suggests.** The 264.2s run had no failures, but it was one run. Raise the cap
  and watch `runs.jsonl` for a fortnight before trusting it; if the failure rate
  climbs, the fix is not to go back to 4, it is (5).
- **Recommendation 10 and recommendation 5 are the same work.** Every one of
  these will be fixed by putting an `until()` where the sleep is, and none of
  them can be reproduced by running the script on its own — which is why they
  have survived sixty runs each.

A repeat-runner under deliberate load is what would find the rest:
`JOBS=8 node tools/test/all.js` in one shell and the suspect script in a loop
in another.
