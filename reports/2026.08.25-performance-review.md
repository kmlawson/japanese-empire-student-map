# Performance, measured on desktop and mobile

**Date:** 25 August 2026, against `40a3de3` (v1.31).
**Method:** headless Chrome with `Emulation.setCPUThrottlingRate` at 4× or 6×,
`Profiler` sampling at 60 µs, the call tree reassembled so every layout-forcing
read is attributed to its caller. Frame gaps from a `requestAnimationFrame`
chain. 2–3 repetitions a row. Nothing in the repository was modified.

**These are the review pass's measurements, not re-run by me.** They are quoted
as reported, with the scripts named so any of them can be checked. Where a
proposed fix was prototyped and measured, that is said; where it was only
reasoned about, that is said too.

**One thing it got right that is worth copying.** The build was pinned with
`git archive HEAD` into a scratch directory and served from there, because this
checkout was being edited while the sweep ran — `map.js` changed at 07:46, mid
sweep. That sweep was discarded and everything re-run against the pinned copy.

---

## A methodological trap, and a bug it exposed in our own tool

`map.js` persists `labels`, `graticule`, `indiaRivers`, `projection`,
`occSource` and the annotation set in `localStorage`. **A second page in the
same browser therefore starts where the first finished**, so a script that
"switches labels on" on page two actually switches them *off*.

`tools/compare_perf.js` had exactly this bug: one browser reused across targets
and repetitions, so every `--admin` run after the first was measuring something
other than what it claimed. Fixed — each measured page now gets its own
`createBrowserContext()`.

## Ranked by how much a reader would feel it

### 1. A pinch runs at half frame rate, and 56% of the main thread is forced layout

Phone 390×780, India, 30 steps in and 30 out, 6× throttle:

| | busy | forced layout | p50 | p90 |
| --- | ---: | ---: | ---: | ---: |
| as shipped | 6,109 ms | 3,353 ms (55%) | **32.5 ms** | 70.0 ms |
| prototype fix | 4,755 ms | 443 ms (9%) | **17.4 ms** | 67.0 ms |
| | −22% | **−87%** | 60 fps | |

Two calls do all of it, both once per pointer move:

```
1,994 ms  getBoundingClientRect  <-  uiBoxes < placeLabels < (anon) < (root)
1,158 ms  getScreenCTM           <-  clientToSvg < pinchState < onPointerMove
```

`placeLabels` runs in the once-a-frame `requestAnimationFrame` in `applyView`
and opens with `uiBoxes()` (`map.js:2448`), which reads the container's
rectangle plus a rect and an `offsetParent` per floating panel. On a pinch,
`rescale()` has just written 2,222 `transform` attributes, so the document is
wholly dirty and each read costs a full layout of a 7,385-node SVG. `pinchState`
(`map.js:3052`) then asks for the screen CTM again, for a conversion the drag
path already does with arithmetic.

The prototype caches `uiBoxes` and gives `pinchState` an `svgFromClient` that
computes from `view` and the container box. The viewBox lands in the same place
— `39.99 496.48 440 815.69` against `40 496.48 440 815.69`, one hundredth of a
unit of rounding. The panels do not move while the map does, so the cache needs
invalidating on a resize, on the info card opening or closing, and on the legend
folding — not per frame.

Work per 30-step pinch: 60 `applyView`, 61 `getScreenCTM`, 60
`getBoundingClientRect`, **75,330 `transform` writes**.

**Caveat, stated by the reviewer.** `Input.dispatchTouchEvent` fires one
uncoalesced `pointermove` per finger, so the test drives `applyView` twice per
step where a real browser would coalesce. Both builds were driven identically,
so the −22% / −87% delta stands; the absolute 6,109 ms is probably an
overstatement of perhaps 2×.

The same fix elsewhere: phone drag layout 101 → 10 ms with busy unchanged;
desktop pan layout 416 → 309 ms (India) and 572 → 336 ms (China), busy unchanged
within noise. So it is a pinch fix, and free tidiness everywhere else.

### 2. Switching projection freezes the page for half a second

4×, home view, 1500×950. "Longest" is the single longest task — the freeze:

| | busy | longest task | with Administrative on |
| --- | ---: | ---: | ---: |
| Albers conic | 612 ms | **498 ms** | 782 / **664 ms** |
| Lambert azimuthal | 588 ms | **483 ms** | 803 / **686 ms** |
| back to Web Mercator | 59 ms | 0 | 96 / 0 |

Self time: `moveD` 219 ms, `albersRaw`/`laeaRaw` 44–95 ms, `setAttribute` 55 ms.
`reprojectDocument` re-parses every `d`, densifies to a point per degree and
re-projects, every time. Going back to Mercator is nearly free because `__d0`
holds the original — **which is the shape of the answer**: cache the projected
`d` per mode the same way, and a second visit to Albers costs a `setAttribute`
loop (~60 ms at 4×) rather than 500. The first visit still costs what it costs.
The memory of holding three copies of 1,246 path strings was not measured.

On a mid-range phone this is 4–8× worse again: two to four seconds of frozen
page for a control offered in a dialog.

### 3. Six and a half seconds to a map on a slow connection

| | first paint | map drawn | wire bytes |
| --- | ---: | ---: | ---: |
| desktop, no throttle, localhost | 52 ms | 111 ms | 3.86 MB |
| phone, 4× CPU, localhost | 104 ms | 390 ms | 3.86 MB |
| phone, 4× CPU, 9 Mbps 4G, gzipped | 300 ms | 1,577 ms | 1.13 MB |
| phone, 6× CPU, 1.6 Mbps, gzipped | 846 ms | **6,343 ms** | 1.13 MB |

The base SVG arrives at 5,938 ms of that 6,343: 821 KB gzipped, **73% of
everything sent before the map exists**, and nothing can be drawn until it
lands. Parsing and building are cheap beside it — 390 ms at 4× CPU with no
network at all.

### 4. Hovering costs more than dragging on a desktop

A 60-step mouse sweep, nothing pressed, 6×:

| region | busy | p90 | p99 | self time |
| --- | ---: | ---: | ---: | --- |
| India | 1,153 ms | **33.5 ms** | 100 ms | `querySelectorAll` 44, `getBBox` 30 |
| home | 849 ms | 25.8 ms | 80 ms | `querySelectorAll` 33, `getBBox` 21 |
| China | 847 ms | 21.4 ms | 67 ms | `querySelectorAll` 22, `getBBox` 11 |

Roots: `onHover` 78 ms, `fillSlot` 35, `outlineOf` 23, `setHot` 18. A drag over
the same ground holds p90 at 18.8 ms; a hover halves it to about 30 fps. Each
new country under the pointer rebuilds a masked outline. Caching the outline per
cluster id is the obvious move; not measured.

### 5. 200 named annotation marks nearly double a pan — the names, not the redraw

4×, 1500×950, 40-step drag:

| | pan busy | redraw | keystroke in Name | Weight slider step |
| --- | ---: | ---: | ---: | ---: |
| none | 359 ms | 9.2 ms | 0.1 ms | 0.1 ms |
| 10 points | 409 ms | 8.4 ms | 8.2 ms | 7.4 ms |
| 50 points | 408 ms | 9.3 ms | 10.6 ms | 9.3 ms |
| 200, names off | 531 ms | 12.2 ms | — | — |
| 200, names on | **695 ms** | 15.7 ms | 19.2 ms | 15.8 ms |
| india-rivers (63 features, 14,851 pts) | 647 ms | 29 ms | 36 ms | — |

**`redraw()`'s `innerHTML = ''` is not the problem at 200.** The floor with
*zero* marks is 9.2 ms, because `redraw` ends in `host.rescale()`, which walks
the map's own 2,222 scalables; 200 marks add 6 ms on top. It matters only at
14,851 points, where it is 29 ms — and lands on **every keystroke** in the Name
field (`fieldChanged`, `annotate.js:749`) and every step of the Weight and
Opacity sliders (`styleChanged`, `annotate.js:762`), both on `input`. 36 ms at
4× is ~150 ms on a phone: a text field that cannot keep up with typing.
Debouncing those two behind a `requestAnimationFrame`, and rebuilding only the
selected feature, is the shape of it. Not measured.

Loading the big file: 558 ms busy at 4×, 1,376 nodes. Opening the tool at all:
74 ms at 4× including fetching `annotate.js`.

### 6. The graticule rewrites its labels every frame

40-step drag, 6×, India: 543 ms off, **663 ms on (+22%)**. Over 38 frames:
**431 `text-anchor` writes and 431 `transform` writes** — twelve labels rewritten
unconditionally every frame by `placeGratLabels` (`map.js:1157`), plus a
`querySelector('#markers')` from `placeGratGroup`. The positions must move; the
`text-anchor` need not, and the whole call could be skipped when the view has
not changed. Worth about 120 ms a drag.

## Two results that overturn what we assumed

**India is no longer the worst case.** China and Japan are, by 20–50% of busy
time — the fine-coastline graft firing mid-gesture (49–219 ms) plus
`ensureSubLabels` calling `getBBox` on the new rings (67–93 ms). At 1500×950,
India is now the *cheapest* of the four non-home regions.

**Turning the Administrative layer on makes a pan cheaper, not dearer.**
1,751 → 1,588 ms at India; 2,647 → 2,420 at 1100×800 China. Consistently, in
all ten paired rows. The divisions replace the whole-country backing, so the
browser rasters more, smaller shapes instead of one huge one. That is the
opposite of what the layer has been suspected of all along.

## Checked and found nothing wrong

- **Desktop panning.** p50 at vsync — 16.6–17.4 ms — in all twenty rows, at 6×,
  every region, every layer. It does not break until 10×.
- **Touch dragging**, phone and tablet, every region, admin on and off: p50
  16.6–16.8 ms, and it survives a 16×-slower CPU. A phone dragging holds 60 fps
  at the median where the desktop breaks first, because the desktop is
  rasterising four times the pixels.
- **The selection mask on the zoom buttons.** `map.js:3144` records a pan
  costing 2.4–3.6× with a territory selected and deliberately does not drop the
  selection for the buttons. Measured directly: the difference is 2–6%.
  `dropForGesture` closed the hole.
- **The URL writer.** Debounced at 400 ms; one `replaceState` per settled
  gesture, none during a 40-step drag.
- **`containerSize()`, `defaultView()`, `islandQuota()`** — all correctly
  cached. One `getBoundingClientRect` and 78 `getBBox` per layer toggle, not per
  label as the profile's shape first suggested.
- **`applyGazetteer`** over ~890 entries: 6–8 ms a drag.
- **Idle cost: zero.** Two seconds untouched produced no attribute writes, no
  layout reads, no work.

## Suggested order

1 first — it is the only gesture on any device that misses vsync at the median,
and it has a prototype with numbers behind it. Then 6, which is small and
certain. Then 2, where the answer's shape is already known from how cheaply
Mercator restores. 5 matters only to somebody annotating a large file, but a
text field that cannot keep up with typing is a bad thing to ship. 4 wants
measuring before touching. 3 is the base SVG's size and is a different kind of
project.
