# The two central scripts, read by hand: map.js's frame path and trains.js

15 September 2026. Read alongside the four investigations of the same day
(`2026.09.15-structure-review.md`, `-duplication-review.md`, `-tests-review.md`,
`-pan-zoom-performance.md`). This note is what one reader found in the two
scripts that matter most, and what to do about it; the measured figures are in
the performance report.

## map.js — what runs when the map moves

`onPointerMove` (map.js:7384) applies the view **synchronously on every
pointer event**: `applyView()` at 7489. Pointer events arrive faster than
frames on a fast mouse, and `applyView` (5903) does real DOM work each time:

* `svg.setAttribute('viewBox', …)` — the one thing that has to happen.
* `scheduleUrl()` — cheap, debounced.
* `$('#zoom-reset')` — a `querySelector` per event (5924).
* `drawGraticule()` if the graticule is on.
* `reliefFade()` and `railFade()` — and `railFade` (2194) is not a fade: it
  ends in `applyAir()`, `syncMapButtons()` and `syncLayerInfo()`.
  `syncMapButtons` (2500) calls `themesHere()`, `trainZone()` (four
  unprojections and a box test), `groundHere()` (another four), `railsAllOff()`
  and `$('#row-train-tools')` — per pointer event, to decide things that only
  change when the *centre* crosses a box edge.

The rest — `rescale`, `syncTrainTools` (added 13 September for the panned-away
rule), `applyGazetteer`, `placeLabels` — is already batched into one
`requestAnimationFrame` (5944–5983), and `placeLabels` is throttled by
`PLACE_MS` during a drag. So the shape is right; the leak is that the
synchronous half of `applyView` still carries button-sync work that belongs
in the rAF half, and `railFade` does more than its name.

**Actions (small, safe):**

1. Move `railFade()`'s tail — `applyAir()`, `syncMapButtons()`,
   `syncLayerInfo()` — out of the per-event path into the rAF block of
   `applyView`, guarded so a state change (which calls `railFade` directly)
   still syncs immediately. Effort S. Guarded by `keys`, `sugar`, `jprails`,
   `trains`, `mntrains` (all press the map buttons).
2. Cache `#zoom-reset` beside `btnStaEl` and the other button handles
   (2501). Effort S.
3. Coalesce pointer moves: in `onPointerMove`'s drag branch, store the target
   view and call `applyView` from a rAF if one is not pending, rather than per
   event. `applyView` already has `rafPending`; the change is to defer the
   viewBox write too. Effort S–M; measure first (the performance report has the
   per-frame figures) — on a 60 Hz mouse this may be nothing.

## trains.js

The module is clean and small (1,928 lines, half of it argument). What I would
change:

1. **`rescaled(k)` (1833) parses each visible mark's `transform` with a regex
   on every zoom frame** to keep the translate and replace the scale.
   `livePos[i]` already holds the position; write
   `translate(livePos.x livePos.y) scale(k)` from it. Effort S. Guarded by
   `trains` (the "same screen size at two zooms" check).
2. **Stale reader-facing wording** since the Manchurian connections were routed
   (13 September): `waitingCard` (1267–1269), `lineCard` (1383–1387) and the
   chip title (1469) still say "drawn straight between cities; alignment
   unsourced" for every `x` line. The bar's own checkbox tooltip was corrected;
   these three were not. Effort S; reader-facing, one sentence each.
3. `buildBar` (1461–1470) calls `data.lines.indexOf(l)` three times per line
   inside a `forEach` that already has the index. Cosmetic.
4. `hitAt`/`linesAt` (1028, 1064) walk every point of every stretch — 34,000
   for Korea — but only on a press, not on hover (map.js:8121, 14022), so they
   are not on the hot path. Leave them.
5. `deriveOwns` (482) is kept only so `tools/test/owns.js` can compare it with
   the Python; `data.owns` is shipped. Worth a comment saying so, not removal.
6. `rgbOf`/`lum` (141–174) duplicate map.js's `fillLum` arithmetic; the
   duplication report will say whether the host should hand them over.

## Not touched

The chord-versus-traced bookkeeping (`splitParts`, `lineFeatures`), the
timetable split (`needTimes`/`setTimes`), and the card builders are the
right shape and are what the tests hold.
