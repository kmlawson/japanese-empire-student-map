# Six bugs, found by review and reproduced

**Date:** 25 August 2026, against `a3c1900` (v1.30).
**Method:** a read-and-verify pass over `map.js` and `annotate.js` driving the
real page on `localhost:8123` through headless Chrome. Nothing in the
repository was modified. Every finding below has a script that reproduces it
and measured output; the numbers quoted are what those scripts printed.

**Two of them I re-ran myself**, independently of the review pass, and both
reproduced — those are marked *confirmed twice*. The other four are the review
pass's own measurements, quoted as it reported them; the reproduction steps are
given so you can check any of them in a couple of minutes.

Nothing here has been fixed yet. Ranked by how much a reader would feel it.

---

## 1. Okinawa disappears when the projection is changed — CRITICAL

*Confirmed twice.*

**What happens.** Zoom into any island group so its fine coastline loads, then
switch to Albers. The ground under you is replaced by open sea, and five
hundred islands from somewhere else are grafted into the document instead.

**Reproduce.**

1. Open `http://localhost:8123/index.html?bbox=126.5,25.8,128.6,26.9` — Okinawa.
2. Layers → **Equal area, conic (Albers)**.

Measured, before and after the switch:

| | fine paths in the document | fine paths in the Ryukyus | land shapes inside the view |
| --- | ---: | ---: | ---: |
| Mercator | 126 | 126 | **60** |
| Albers | 559 | **0** | **0** |

The screen is empty sea. LAEA escapes, but only by luck — see below.

**Why.** Two independent faults compound, and both are the same mistake:
geometry captured in one projection being used as though it were in another.

*`wantsFine()` — `map.js:5074–5081`.* It decides which coastline windows the
view is looking at by comparing `view.x/y/w/h`, which are in **the live
projection's units**, against the boxes in `#proj[data-fine]`, which the build
writes in **Mercator units**. After a switch to Albers the Okinawa view sits at
x≈1308, which falls outside the Mercator `ryukyu` box (`1138.7, 673.4, 1306.6,
827`) and inside the Mercator `nanyo` box (`1319, 902.5, 2123.4, 1302`). So the
Ryukyus are dropped and **559 Caroline islands are grafted**, drawn at
`1452–2245, 979–1349` — nowhere near the reader.

*`reprune()` — `map.js:5159–5162`.* Dropping a window restores the coarse
shapes from `coarseOrig`, which holds raw `d` strings captured by `remember()`
(`map.js:5188`) under whatever projection was on at prune time. There is no
record of which. So 23 Ryukyu paths come back **in Mercator coordinates** while
the rest of the map is in Albers — about 110 units west and 130 north of where
they belong. The Senkakus, which were never pruned and so never entered
`coarseOrig`, are correctly in Albers, which is how you can see the two sets
disagree.

**Why LAEA looks fine.** Its view coordinates happen still to overlap the
Mercator `ryukyu` box, so nothing is dropped and `reprune` never runs. It is not
a different behaviour, only a different accident.

**Cold links are hit too, more mildly.** Opening
`?bbox=126.33,25.1,128.74,27.6&layers=pcw` — an Albers link the map wrote
itself — gives 0 fine paths in the Ryukyus and 559 in the document: the fine
coast never arrives at all, so the reader gets Natural Earth's blocky Okinawa
plus 559 needless shapes.

**Related, same family, not separately demonstrated.** `rebuildFineHits()`
(`map.js:5282`) runs only from `syncFine`, so after a reprojection that changes
nothing else, `fineHits` still holds Mercator boxes and `nearestFine`'s reach
for a reef just off the pointer silently stops working.

**Note.** This is the same shape as the Japan bug fixed in `519e934` — state set
when a window grafts and not corrected when the world changes underneath it —
one projection over.

## 2. A finger cannot move a mark, and the press kills the pan too — HIGH

**What happens.** On a phone or tablet, pressing one of your own annotation
marks and dragging does nothing at all: the mark stays put *and* the map does
not pan.

**Reproduce.** Place a point, put the tool away, press the mark and drag 120 px.
Mouse viewport uses the `matchMedia` shim; the finger viewport is
`isMobile: true, hasTouch: true` with the shim off, driven by
`mouse.down()`/`mouse.up()`.

```
MOUSE
  coord before : 37.3°N, 138.82°E
  coord after  : 29.24°N, 153.31°E
  moved: true    map panned: false    message: "Moved."

FINGER
  coord before : 33.07°N, 133.11°E
  coord after  : 33.07°N, 133.11°E
  moved: false   map panned: false    message: "Placed on Japan."
```

**Why.** `annApi.drag()` has exactly one call site — `map.js:3924`, inside
`onHover`, which is a `mousemove` listener wired only when `hoverCapable`
(`map.js:2922–2923`). On a coarse pointer nothing ever calls it. `grab()` still
fires on `pointerdown` and sets `dragStart = null; movedFar = true`
(`map.js:2981–2985`), so the map's own pan is cancelled as well. The gesture is
dead rather than degrading to something.

## 3. Opening a shared link silently destroys your own saved annotations — HIGH

*Confirmed twice.*

**What happens.** You have unsaved marks. A classmate sends you a shared link.
You click it, and your work is gone — from the screen and from the browser's
store — with no prompt and no message.

**Reproduce.**

1. Draw some marks and leave them (they are kept in the browser automatically).
2. Open a `?ann=…` link made from a different set.

Measured:

```
dialogs shown to the reader : []
their saved set is now      : ["SOMEBODY ELSE'S MARK"]
```

`MY FIRST MARK` and `MY SECOND MARK` are gone from `localStorage`.

**Why.** `fromUrl` (`annotate.js:1409–1421`) calls the *internal* `open(true)`,
which skips `offerRestore()`. `loadText` then replaces `feats` outright
(`annotate.js:962`) and `changed()` → `store()` (`annotate.js:114–121`) writes
over `localStorage['jem-annotations-v1']`. Undo would bring them back in memory,
but the reader is never told there is anything to undo, and a reload makes it
permanent.

**Compare `Clear`,** which asks before removing the same work. This path does
not.

## 4. Multi-geometry vertices get handles that cannot drag, and each try burns an undo step — MEDIUM

**What happens.** Load anything exported from QGIS or Natural Earth — which
lands as `MultiPolygon` — select it, and its corners show drag handles. Dragging
one does nothing. Undo then reports "Undone" without undoing anything.

**Reproduce.** Load a `MultiPolygon` or `MultiLineString` file, select it, grab
a vertex handle, drag, then press Undo twice.

```
MultiPolygon
  vertex handles drawn : 8       handle grabbed: {r:"1", v:"3"}
  geometry moved       : false
  after one Undo       : "Undone."  features left: 1   ← nothing had changed
  after two Undos      : "Undone."  features left: 0

MultiLineString
  vertex handles drawn : 4       handle grabbed: {r:"1", v:"1"}
  geometry moved       : false
  after one Undo       : "Undone."  features left: 1
  after two Undos      : "Undone."  features left: 0
```

**Why.** `redraw()` draws handles for every ring `ringsOf()` returns, and
`ringsOf` flattens all seven geometry types (`annotate.js:327–338`). `drag()`
handles only `Point`, `LineString`, `MultiPoint` and `Polygon`; everything else
hits the `else` at `annotate.js:644` and clears `dragging`. Because `dragging`
is already null, `drop()` returns false and never reaches its `undoStack.pop()`
(`annotate.js:650–657`), so the snapshot `grab()` took at `annotate.js:610–625`
is left on the stack.

**A trap in the obvious fix.** `r` is an index into the *flattened* ring list,
so adding a `MultiPolygon` branch to `drag()` is not enough — `g.coordinates[r]`
is a polygon there, not a ring. The index has to be rebuilt.

## 5. Sub-labels leak on every fine-window round trip — MEDIUM

**What happens.** Moving between island groups makes the map progressively
slower, for nothing visible.

**Reproduce.** Okinawa with place names on. Zoom out five notches (far enough to
drop the `ryukyu` window) and back in, four times.

```
start (ryukyu)   subText 591    dead 77    fine 126
 k1 back in      subText 767    dead 253   fine 126
 k2 back in      subText 943    dead 429   fine 126
 k3 back in      subText 1119   dead 605   fine 126
 k4 back in      subText 1295   dead 781   fine 126
```

**+176 permanently dead `<text>` elements per round trip, unbounded.**

**Why.** `graftFine` builds fresh nodes with `document.importNode`
(`map.js:5256–5262`), so the `subLabelled` WeakSet never recognises them:
`ensureSubLabels` makes a new `<text>` plus new entries in `labels`, `subLabels`
and `scalables` every time (`map.js:2513–2555`). Nothing removes them.
`gateLabels` only hides them, because `L.owner.isConnected` is false; and
`composeEpoch` filters `scalables` by `isConnected`, which these dead nodes
still are, since they live in `labelLayer`.

**Why it matters.** `rescale()` walks `scalables` on every zoom frame, and
`gateLabels`/`placeLabels` walk `labels` on every zoom and pan. It also keeps
invalidating `islandQuota`'s cache, whose key is `labels.length`.

## 6. `rank[…] || 2` demotes country names below every island — LOW

**What it is.** `rank.territory` is `0`, and `0 || 2` is `2`. Country labels
therefore tie with sub-units, and since a territory entry has no `area`, the
`(b.area||0) - (a.area||0)` tie-break puts it behind every island with a
measured box. `map.js:2577`. The comment eighteen lines above states the
invariant this breaks: *"Country names first, then divisions, then the rest: a
province must never crowd out the country it is in."*

Order `placeLabels` then walks, first getting the space:

```
1. Kwangtung (division)   rank used = 2
2. Okinawa (island)       rank used = 2
3. a 4-pixel islet        rank used = 2
4. Japan (country)        rank used = 2
5. Tokyo (site)           rank used = 3
```

**Honest caveat, and the reason it is last.** The review pass could not make it
bite a reader. It probed deep views at Okinawa, the western Solomons, Taiwan,
Chōsen, the wide Solomons and the Carolines; in every one the country name that
was on screen was still placed, and no territory label was hidden with its
anchor in view. The `NUDGES` fallback appears to absorb it. **Confirmed as a
code defect, unconfirmed as a reader-facing one.**

## Checked and found nothing

Worth recording, so the same ground is not covered twice:

- **`syncBackings` against `reprune` ordering.** A one-cycle lag was expected —
  the backing hidden on stale `superseded` classes. It is correct: `syncFine`
  calls `reprune()` and *then* `applyState()`, which calls `syncBackings`.
  `loadAdmin` and `setProvinceSource` also end in `applyState()`.
- **`defaultView` / `homeCache`.** The defensive copy is present and correct;
  the cached object is never handed out. (This was a real bug once — see
  `docs/tasks.md`.)
- **`bumpLayout` coverage.** `applyState`, `composeEpoch`, `onResize`,
  `replaceInProjection`, `graftFine` and `dropFine` all bump. `loadAdmin` and
  `setProvinceSource` reach `applyState`, which does.
- **`bboxOf` / `hiGen` / highlight slot keys.** `dropFine` alone does not
  `bumpHi`, but it only runs inside `syncFine`, which always `reprune()`s
  afterwards, and that does.
- **The annotation link, packed and unpacked.** A 451-character round trip
  through `CompressionStream('deflate-raw')` opened correctly in a second page.
- **The undo stack generally.** `drop()` correctly pops for a press that never
  moved; `loadText`, `removeAt`, `finish`, `tap` and Clear all snapshot before
  mutating. Only the path in bug 4 leaks an entry.
- **Marquee, pinch, double-tap and one-finger zoom, the `pointers` map, capture
  release.** Read closely, nothing reproducible.
- **`pick` / `provinceAt` / `nearestSubUnit` / `recordFor`, and the two-tap
  rule.** Read closely, nothing reproducible.

## Two suspicions, reasoned but not demonstrated

Recorded because they are worth a look, not claimed as bugs:

- **`homeBounds()` (`map.js:1925`) projects only two corners** — the same
  Mercator-only assumption `viewForBox` was fixed for, and it feeds the phone
  and wide-desktop `cropToHome` opening view. The Albers and LAEA reset views do
  differ from Mercator's, but neither could be shown framing the wrong ground.
- **`islandQuota`'s `quotaAt` cache can go stale across a reprojection** —
  `size` and `labels.length` can both be unchanged while every `L.x`/`L.y` has
  moved. Reasoned from the code; no wrong outcome observed.
- **`geomOK` accepts an empty `GeometryCollection`** — `[].every()` is `true`
  (`annotate.js:702–704`), giving a feature that draws nothing and reports no
  error. A nit.
