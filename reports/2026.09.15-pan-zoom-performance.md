# Low-hanging fruit for faster pan and zoom

**Date:** 15 September 2026, against `c46edd8`, version 1 update 372.
**Scope:** the pan and zoom frame path only, and only changes of at most a few
dozen lines. Nothing in the repository was modified by this review except this
file; every experiment ran against a copy of `deploy/` under `/private/tmp`.

## Method

* The frame path read end to end in `map.js` — `applyView`, `rescale`,
  `gateLabels`, `placeLabels`, `applyGazetteer`, `applySizedSites`, `railFade`,
  `reliefFade`, `syncMapButtons`, `syncTrainTools`, `trainBoxAt`, and the
  pointer handlers.
* Measured in headless Chrome (Puppeteer, `tools/test/suite.js`'s `launch`/
  `ready`/`SHIM`), CPU throttled 4x as the project's own `tools/stats.js` and
  `tools/compare_perf.js` do, so the figures compare with the August sweep.
  Server on port 8125 from the repository root.
* Views: whole empire, Korea at ~6 degrees, and a deep zoom over Keijo.
  Layer states: nothing on; Korea + Japan railways; train tools up; admin
  divisions on.
* Three instruments, because they answer different questions: V8 precise
  coverage with call counts (what runs, and how often, per frame); the CPU
  sampling profiler at 100 us (which function the time is in); and Chrome's
  `Performance.getMetrics` counters for `ScriptDuration`, `RecalcStyleDuration`
  and `LayoutDuration`, which is the only one of the three that sees the style
  and layout work a change to the DOM causes.
* Forced layout was found by wrapping `getBoundingClientRect`, `getBBox`,
  `getScreenCTM` and `getComputedTextLength` in `evaluateOnNewDocument` and
  counting callers by stack.
* Candidate fixes were applied to a copy of `deploy/` under `/private/tmp`,
  served on port 8126, and measured against the untouched build on 8125.

P1 and P2 between them have done what the survey said they would: **there is no

in the page and counting callers over a 40-step drag gives, at every view and
every layer state measured, exactly two entries — one `containerSize()` and one
burst of 77 `getBBox` from `activeBounds()` (`map.js:5049`), both once per
gesture, not per frame. The rest of the list is the hover at the end of the
drag. That is a clean result and the frame path should be kept that way.

## The frame path as it stands

**Every pan frame** (`applyView`, `map.js:5903`), synchronously:
`clampView` → `viewBox` write → `scheduleUrl` → `defaultView` (cached) →
`$('#zoom-reset')` (a `querySelector` per frame) → `drawGraticule` if on →
`reliefFade` → **`railFade`** → then one rAF holding `syncTrainTools`,
`applyGazetteer`, and `placeLabels` throttled to 10 Hz.

**Every zoom frame:** the same, plus `rescale()` — which walks all 2,445
scalables — plus `gateLabels`, `applySizedSites`, `placeLabels` unthrottled,
and a **second** `railFade` (`rescale` calls it at `map.js:6151`, after
`applyView` has already called it at `map.js:5938`).

Call counts taken from V8 precise coverage over one 40-step drag (38
`applyView` calls). **Per pan frame:**

```
railFade            1     railFadeOne     6     railAlpha       3
syncMapButtons      1     railUnderView   2     railZone        1
syncLayerInfo       1     layerInfoOn     7     themesHere      1
syncTrainTools      1     trainBoxAt      1     trainZone       1
applyGazetteer      1     reliefFade      1     containerSize   4
viewLonLat          6     viewMeets       6     unproject      27
```

Six `viewLonLat` per frame is six independent recomputations of the same
rectangle, each unprojecting four corners; `groundHere` runs three times and
`railUnderView` twice because three separate callers in `syncMapButtons` ask
the same question.

## Finding 1 — `railFadeOne` rewrites every railway tie on every pan frame

`map.js:2917`:

```js
$$('path.rail-tie', group).forEach(function (el) {
  el.style.opacity = String(t);
});
```

`railFade` is called from `applyView` on **every** pan frame (`map.js:5938`)
and again from `rescale` on every zoom frame (`map.js:6151`), and it calls
`railFadeOne` six times. With Japan's railways on that group holds **1,977 tie
paths**, so a pan does a `querySelectorAll` over the group and 1,977 inline
style writes sixty times a second — for a value, `t`, that depends only on
`view.w` and therefore **cannot change during a pan at all**.

Measured on a copy of `deploy/` served on another port, Korea at 6°, Korea's
and Japan's railways on, 40-step drag, CPU/4, median of three:

```
                     script/frame   busy, whole drag
  as it is                4.70 ms        187 ms
  tie list cached         0.97 ms         39 ms
```

**−3.7 ms of script per pan frame at 4x — about 1 ms a frame unthrottled, and
148 ms off a one-second drag.** With the fix, panning with the railways on
costs what panning with nothing on costs (0.85 vs 0.78 ms/frame); without it,
it costs six times as much. This is the largest single item found, and the
change is nine lines.

The sketch, in `railFadeOne`:

```js
if (!group.__ties || group.__tieN !== group.childElementCount) {
  group.__ties = $$('path.rail-tie', group);
  group.__tieN = group.childElementCount;
  group.__tieT = null;              // new nodes have not been written yet
}
if (group.__tieT !== t) {
  group.__tieT = t;
  var ts = String(t);
  for (var i = 0; i < group.__ties.length; i++) group.__ties[i].style.opacity = ts;
}
```

The count test outside the `t` comparison matters: `applyState` inserts a tie
and a hit band beside every rail path (`map.js:15504-15510`), so the node list
has to be re-taken when the group grows — and the ties it has just made have
had nothing written to them, which is why `__tieT` is cleared there and not
only where `t` changes.

**Verified** by reading the first tie's opacity in `#kr-rail` and `#jp-rail` at
the opening view, six notches in and twelve notches out, and after a pan:
identical strings from both builds (`0` / `0.517451` / `0` / `0`).

**Risk:** a stale node list if ties are ever added without changing the group's
child count. Nothing does that today — ties and hit bands are inserted as a
pair with the path — and the count test catches the grafts (`jp-rail` arrives
whole, `tw-sugar` is its own group).

## Finding 2 — `gateLabels` forces a layout of the whole document on every zoom frame

`map.js:6632-6654`. The write-then-read batching is right and the comment
explaining it is right, but the batch is read **inside the zoom frame**, a few
lines after `rescale()` has written 2,445 transforms. The first
`getComputedTextLength` therefore flushes a full layout of a ten-thousand-node
SVG, once a frame, for as long as the reader keeps turning the wheel.

Korea at 6°, Names on, 12 wheel steps, CPU/4, median of three:

```
                                     busy      getComputedTextLength self
  as it is                          852 ms          292-389 ms
  measurement deferred to settle    558 ms             absent
```

Counting what is actually measured: between 0 and 71 labels per frame, ~410
over the whole gesture, so the cost is not the number of measurements — it is
the one forced layout each frame pays for the first of them.

Two things were tried. **Caching the measured width by text** (widths are in
local units and do not change with `k`, so the cache is sound) saved almost
nothing — 750 → 741 ms — because the names arriving are new ones, not names
coming back. **Deferring the whole read to the settle** is what pays: keep the
`measure` list on the module instead of in the call, return before the read
loop while a gesture is live, and drain it in the 220 ms settle timer that
already re-runs `placeLabels` (`map.js:5997-6006`). Between the frames the
placer uses `estimateWidth`'s guess, which is what it already uses for the
frame in which a name first appears.

**Verified:** the visible label set — text plus transform, sorted — is
identical between the two builds before a zoom and after a 4-step zoom and its
settle.

**Risk:** for the ~200 ms of a gesture, a newly arrived name is boxed by the
estimate, which the file's own comment says is short by 11% in the middle of
the distribution. Two names that genuinely fight could both be drawn for a few
frames, and the settle then drops one. That is a real visible change and it is
the author's call whether it is worth 40% of the zoom.

## Finding 3 — `rescale` writes a transform to 847 elements nobody can see

`map.js:6133-6145` walks all 2,445 scalables and writes a `transform`
attribute to each. Counted in the page, **847 of them have
`style.display: none`** at every view measured — 720 of those are the site and
station labels, which `gateLabels` and `placeLabels` hide and show. Writing to
a hidden element is not free: it dirties style for it.

Skipping them, and re-placing anything revealed later in the same frame:

```
  korea / nothing on / 12 wheel steps      style recalc per step
    as it is                                    12.92 ms
    hidden scalables skipped                     7.50 ms
```

Script time is unchanged (the walk still happens, the compare replaces the
write), so this is a **style-recalculation saving of about 5.4 ms per zoom
frame at 4x**, roughly 1.4 ms unthrottled, and it does not show up in the CPU
profile at all.

The shape of it: `if (s.el.style.display === 'none') { s.placedK = 0; continue; }`
in `rescale`, and a `placeRevealed()` — the same loop, placing only entries
whose `placedK` is not the current `k` and which are now visible — called at
the end of the zoom rAF, after `gateLabels`/`applyGazetteer`/`placeLabels` have
had their say (`map.js:5993-6003`).

**Verified** against the case that would break it: the gazetteer's 992 dots
switched off, zoomed six steps, switched back on — every one of the 495
visible dots carries a byte-identical transform in both builds. It survives
because the Cities switch hides the *group*, not the elements, so the elements
never enter the skipped set. The same check over all 2,015 transformed elements
after a zoom plus Names, Korea's railway and Korea's stations switched on found
no difference either.

**Risk:** a path that reveals an element without a `rescale()` or a
`placeRevealed()` after it would leave that element at the previous zoom's
scale. `applyState` is the one to watch — it calls `gateLabels` and
`placeLabels` directly (`map.js:15578-15581`) and never calls `rescale` — so
`placeRevealed()` belongs at the end of it as well. That is the line this
change most easily gets wrong.

## Finding 4 — the same rectangle is worked out six times a frame

`viewLonLat` (`map.js:2338`) unprojects the four corners of the view, and is
called **six times per pan frame**: `railZone`, `railUnderView` twice,
`themesHere`, `themeFollowsView` and `trainBoxAt` all ask, through
`viewMeets`/`groundHere`, and none of them remembers. 27 `unproject` calls a
frame. `applyGazetteer` (`map.js:4407`) separately writes `style.display` to
all 992 gazetteer entries on every pan frame although its only two inputs —
the epoch and `gazMinTier()` — are constant through a pan.

Memoising `viewLonLat` on `view.x,y,w,h` plus `projMode`, and returning early
from `applyGazetteer` when `epoch|floor` is unchanged, measured:

```
  korea / nothing on / 40-step drag, busy     29.7 -> 25.0 ms   (one pair of runs)
                                              29.7 -> 31.0 ms   (medians of three)
```

**So: below the noise floor.** The pan path with nothing on is ~30 ms of
scripting for a whole drag and the run-to-run spread is ±6 ms; these two
changes are worth about 0.1 ms a frame at 4x and cannot be told apart from
noise on this machine. They are correct and they are eight lines, but they
should be sold as tidying, not as speed. Their value is larger under a conic
projection, where `unproject` is not two multiplications.

## Finding 5 — small things on the pan path, unmeasurable individually

* `applyView` does `$('#zoom-reset')` on every frame (`map.js:5923`). Hold it
  the way `syncMapButtons` already holds its six buttons (`map.js:2578`).
* `syncLayerInfo` (`map.js:13023`) runs from `railFade` on every frame, calls
  `layerInfoOn` seven times and `$('#btn-layer-info')` once. Its answer changes
  only when a layer is switched.
* `syncMapButtons` asks `railUnderView()` twice and `railZone()` once
  (`map.js:2643`, `2700`, `2714`); one local would do.
* `rescale` calls `railFade` (`map.js:6151`) which `applyView` has already
  called in the same frame (`map.js:5938`). With Finding 1 in place the second
  call is nearly free; without it, it doubles the cost.
* `defaultView`'s cache is keyed on `layoutGen` (`map.js:5770`), and
  `layoutGen` is bumped by a `ResizeObserver` on the panels — so *closing the
  info card*, which is what `dropForGesture` does at the start of every drag,
  invalidates it and the first frame of the gesture recomputes `activeBounds`:
  **77 `getBBox` calls, one full layout**, once per gesture. The map's drawn
  bounds cannot change because a panel resized. A generation of its own,
  bumped by `composeEpoch`, `replaceInProjection` and the world/East-Asia
  switch, would take that flush off the front of every drag. Six lines.

## Finding 6 — the train tools recompute their own extent from every station, every pan frame

`trainBoxAt` (`map.js:2452`) asks the mounted network where its track actually
is, on every pan frame, and `trains.js:1778`'s `bounds()` answers by walking
**every station in the system** and, for each, a `.some()` over the lines it
sits on. Korea's timetable is a thousand-odd stations. Its answer changes only
when a different system mounts or the connections switch flips.

Korea at 6°, train tools up, 40-step drag, CPU/4, medians of three:

```
                          busy, whole drag      bounds self time
  as it is                     61.8 ms              19.4 ms
  memoised                     34.4 ms               5.6 ms
```

**−27 ms a drag, about 0.7 ms a frame at 4x**, for five lines: a
`boundsKey`/`boundsVal` pair on the module, keyed on the mounted `data` object
and `connOn` — not on `cfg.sys`, since a system whose data has been replaced
must not answer from the old walk. Clear it on mount and unmount.

## The SVG itself

`deploy/japan-empire-map.svg` is **3,816 KB raw, 1,093 KB gzipped** — larger
than the 2.8 MB the August survey measured. Counted:

```
  elements        2,011      of which path 1,324, circle 586, g 72
  data-* attrs    3,264
  <filter>            0      filter= attributes   0
  mask                0      clip-path=           8
  opacity="…"         0      fill-opacity         0
  display:none        6      (on <g>, which is the cheap kind)
  non-scaling-stroke  0      in the file; 32 rules in styles.css
```

So the shipped file is clean: no filters, no masks, no per-element opacity, and
the six hidden layers are hidden with `display: none` on the group rather than
with `opacity: 0`. `railFadeOne` and `reliefFade` both drop to `display: none`
once their ramp reaches nothing (`map.js:2912`, `2071`), which is the right
instinct — a group left at `opacity: 0.001` would be composited every frame.

`styles.css` has **no `will-change`, no `contain`, no `mix-blend-mode`, no
`backdrop-filter`**, and the twelve `filter:` rules are all on hover, selection
or animation states rather than on anything standing. Nothing in the CSS forces
a repaint of the whole SVG on a pan.

The live document is much bigger than the file: **10,372 nodes** at the opening
view, 16,305 with Japan's railways on (jp-rails adds 1,977 paths, each of which
`applyState` gives a tie and a hit band — three nodes per line), 10,889 with
the administrative sheet.

`vector-effect: non-scaling-stroke` on 32 rules is the one structural cost on
the pan path that cannot be tidied away: it makes the browser recompute stroke
geometry for every stroked path on every `viewBox` change. It is also not
negotiable — it is what keeps a coastline one pixel wide at every zoom.

## Labels on a pan

Answering the question directly: **labels are not re-laid-out on a pan.** A
label is a `<text>` in map units inside the SVG, so the `viewBox` moves it for
free; what a pan changes is only which names are in frame and how they crowd.
`placeLabels` — the greedy screen-space collision pass — is throttled to 10 Hz
while a drag is in flight and run once more on the 220 ms settle
(`map.js:5993-6006`, `PLACE_MS`). That throttle is new since the August survey
and is the single largest thing that has made panning cheap.

On a **zoom** frame it runs unthrottled, together with `gateLabels`. Its cost
at Korea with Names on, CPU/4: `placeLabels` itself 6.6 ms per 40-step drag,
`relocate`'s `isPointInFill` 97 ms per 12 wheel steps (8 ms a step at 4x),
`gateLabels`'s forced layout 24-32 ms a step — Finding 2.

`relocate` (`map.js:6802`) tries up to 25 points inside a division's visible
part, each an `isPointInFill`. Starting the search at the point that worked
last frame was tried and measured: **no change** (97.4 vs 98.2 ms), because the
cost is in the labels that fail all 25 tests, not in the ones that succeed on
the first. Left alone.

## What is not low-hanging

So the author knows where the ceiling is:

* **Canvas or WebGL rendering.** It would remove the per-frame stroke
  recomputation and the style invalidation entirely, and it would take the
  hover, the hit-testing, the masks, the annotations and the accessibility of
  an SVG with it. This is a different map, not a change.
* **Tiling, or splitting the base SVG by region.** The fine coastlines and the
  administrative sheet are already deferred; going further means deciding what
  a reader can see before they ask for it, and a new class of bug where the
  ground is missing. A project, as the survey said.
* **Driving all 2,445 scalables from one inherited CSS custom property**
  (`transform: translate(var(--x),var(--y)) scale(var(--k))`, with `--k` set
  once on the root) would turn `rescale`'s 2,445 attribute writes into one.
  It is the obvious big win on the zoom path and it is not low-hanging: it
  moves every scalable's placement from an attribute the code owns to a
  property the stylesheet owns, and it has to be proved in three browsers.
* **Rewriting the label placer** (a spatial index instead of the greedy
  O(n·placed) walk). Worth it only once the forced layout in Finding 2 is gone,
  and then it is a day's work with its own tests.
* **The base SVG's 1.1 MB gzipped.** Unchanged in kind since August: brotli,
  coordinate rounding, and deferring the backing layers. Each needs its own
  measurement pass.

## What it would cost to check

A change to `map.js` implicates the `core` group and, for 1 and 4, `transport`
as well; `node tools/test/all.js changed` will say so and print its reasoning.
The suite's own record (`tools/test/runs.jsonl`) has the **whole suite at a
median 504 seconds** over its last six runs of 69-70 scripts, and a `changed`
