# Performance audit — 17 August 2026

Everything below was measured on this repository unless it is explicitly marked
**inferred**. The harnesses are described in *How this was measured*; the raw
ladders are in the appendices.

The audit was asked to go past what is already on record: that panning is bound
by SVG path rasterisation, that the backings are 48% of the path data and about
three quarters of the raster time, and that the 780 KB gzipped SVG dominates
load. All three are confirmed. But the **reason** the backings cost what they do
is not their vertex count, and the **reason** the SVG is 780 KB is not its
precision. Both of those change what the fix is, and in both cases the fix is
cheaper and safer than the architecture-level surgery the diagnosis seems to
call for.

Two findings carry most of the value:

- **`#backings path { stroke-width: 1.3 }` → `1` takes pan rasterisation down
  by 64%.** One character. It is a Skia hairline threshold, not a geometry
  problem.
- **Emitting path data as relative commands instead of absolute ones takes the
  SVG from 817 KB gzipped to 451 KB — 45% — with every vertex and every
  coordinate value preserved exactly.** It is an encoder change, not a
  cartographic one.

Neither touches the geometry, the sources, or the single-file build.

---

## Part 1 — Rasterisation: the crack-filling stroke, not the geometry

`styles.css` gives the backings and the atoms a stroke in their own fill colour,
1.3 units wide, with `vector-effect: non-scaling-stroke`. It closes the
anti-aliasing hairline cracks between adjacent polygons — a real problem,
correctly diagnosed, and the comments in the file say exactly why it is there.

Skia rasterises a stroke of width ≤ 1 with a cheap hairline rasteriser. Above 1
it must build a stroked outline polygon from the path, and with
`non-scaling-stroke` that outline lives in device space, so it is rebuilt
whenever the CTM changes — which a `viewBox` rewrite does on **every frame of
every pan**. `#backings` is 102,085 vertices. That is 102,085 vertices of stroke
tessellation per frame, and the atoms add their own.

The threshold is sharp. Changing only the two crack-filling widths, nothing else:

| stroke-width | 0.4 | 0.6 | 0.8 | **1.0** | **1.05** | 1.1 | 1.2 | **1.3 (shipped)** | 2.0 |
|---|---|---|---|---|---|---|---|---|---|
| RasterTask over a drag | 147 ms | 148 ms | 147 ms | **149 ms** | **857 ms** | 862 ms | 872 ms | **887 ms** | 933 ms |

One twentieth of a unit either side of 1.0 is a factor of six, and the shipped
value sits just past the cliff.

This also explains the observation already on record that the cost is
"geometry-bound not pixel-bound, flat across devicePixelRatio 1/2/3". Stroke
tessellation is per-vertex and happens before rasterisation, so it *is* flat
across DPR. Confirmed directly, and the hairline threshold is in user units
rather than device pixels, so a DPR-3 phone does not lose the win:

| | DPR 1 | DPR 2 | DPR 3 |
|---|---|---|---|
| shipped (1.3) | 873 ms | 868 ms | 873 ms |
| width 1.0 | 153 ms | 168 ms | 147 ms |

### What this displaces

Three things that look like the cause are not, and each cost real time to rule
out:

- **`#seams` is 12.4% of all path data** (331 KB, 27,513 vertices) **and removing
  it changes pan raster not at all** — 901 ms against an 890 ms baseline. It is
  fill-only with `stroke: none`, which is exactly why: it never enters the
  stroke-tessellation path. Its cost is bytes, not frames.
- **Removing both `clip-path` attributes changes nothing** (907 ms), despite
  `clip-china` being 16,368 vertices.
- **Deleting the entire `#backings` group gives 248 ms.** Narrowing its stroke
  gives 322 ms. So **the one-character change is worth 96% of deleting the
  layer outright** — which means the layer's vertex count was never the
  problem, and the whole question of whether the backings are redundant is
  orthogonal to panning performance.

## Part 2 — Load: the encoding, not the precision

Path data is **96.2% of the SVG file** — 2,742 KB of 2,849 KB. The encoder
(`ring_to_path`, `build_map.py:2702`) writes an explicit absolute `L` with full
coordinates for every vertex: 199,705 `L`, 4,361 `M`, 4,346 `Z`. No relative
form, no implicit lineto, no sign elision. A representative fragment:

```
M457.3 751.7L457.9 751.9L458.3 752.3L458.6 752.7L458.4 752.5L458.5 752.7
```

Because neighbouring vertices are close together, the deltas are far shorter
than the absolute values. Re-encoding with relative `l`, implicit lineto and
sign elision — **same 2-decimal precision, same viewBox, every vertex kept,
error accumulated on the printed grid so it cannot drift**:

| | raw | gzip | brotli |
|---|---|---|---|
| shipped (absolute `L`, 2 dp) | 2,849,764 | 817,322 | 441,847 |
| **relative `l`, identical precision** | **1,887,678** | **450,978** | **328,578** |
| | **−34%** | **−45%** | **−26%** |

**45% off the gzipped payload with no change to the drawing whatsoever.** On the
load figures already on record (1,503 ms / 5,625 ms on slow 4G) that is roughly
1.8 seconds off "map on screen", from a change to one function.

It also takes 940 KB off the raw file, which matters for the 4.5 MB standalone
bundle, read from disk uncompressed.

### If you want more than lossless

Going further means changing the coordinate grid, and the honest way to judge it
is against the deepest zoom the map allows. `MAX_ZOOM = 100`, so the tightest
view is 28 units across 390 CSS px: **one unit is 13.9 CSS px at maximum zoom**
and 0.497 CSS px at the opening view on a phone.

| encoding | gzip | vs shipped | worst-case error at `MAX_ZOOM` |
|---|---|---|---|
| shipped, absolute, 2 dp | 817 KB | — | 0.14 CSS px |
| **relative, 2 dp (lossless)** | **451 KB** | **−45%** | **0.14 CSS px** |
| relative, integers on a 40× grid | 361 KB | −55% | **0.17 CSS px** |
| relative, integers on a 20× grid | 323 KB | −59% | 0.35 CSS px |
| relative, integers on a 10× grid | 288 KB | −64% | 0.70 CSS px |
| + Douglas-Peucker 0.1 u, 10× grid | 233 KB | −71% | 1.39 CSS px |
| + Douglas-Peucker 0.2 u, 5× grid | 159 KB | −80% | 2.78 CSS px |

The **40× grid is the last rung that is provably invisible**: a half-step of
0.0125 units is 0.17 CSS px at the deepest zoom the map can reach, so no vertex
can move by a visible amount anywhere. It removes no vertices — it writes the
same points on a grid still finer than the screen can resolve. −55% for that is
a good trade and it does not engage the "never simplify unasked" principle at
all, because nothing is simplified.

Below that rung you are trading visible fidelity for bytes, and §9 sets out the
one shape of that trade I think is defensible.

### A latent bug worth fixing on the way past

3.2% of the main file's vertices (6,488) and **5.7% of the admin file's (4,900)
are exact duplicates of the previous point** — they print identically, so they
are already not in the drawing. The cause is that `FINE_PRECISION`
(`build_map.py:2699`) dedupes at 0.002 but prints on a 0.01 grid, so points that
round to the same printed pair survive the dedupe. About 155 KB of noise, and no
measurable raster cost (960 ms, within noise), so fix it for the bytes and
because it is a bug, not for the frames.

## How this was measured

`puppeteer-core` driving Chrome 152 headless against a byte-identical copy of the
repo served over `http://localhost`. Each variant is that copy with exactly one
file replaced, so nothing else moves.

- **Pan harness.** 390×844, `deviceScaleFactor: 2`, `isMobile`/`hasTouch`,
  `Emulation.setCPUThrottlingRate: 4`. Load, settle 2.5 s, then a 14-step touch
  drag (8 px right, 4 px down per step, 24 ms apart) over roughly 1.6 s at the
  opening 1930 view (`viewBox` 785.4 units wide), Administrative **off**, which
  is the default. `RasterTask` summed from a `devtools.timeline` trace of the
  drag. 2–4 repetitions per variant; spread between repetitions is about ±8%, so
  differences under 15% are reported as "no change".
- **Hover harness.** 1440×900, DPR 2, 4× throttle, 51 `mousemove`s sweeping
  across China at 5 px steps. `matchMedia('(hover: hover)')` is stubbed true,
  because headless reports `hover: none` and would otherwise skip `onHover`
  entirely — worth knowing if anyone re-runs this.
- **Function-level attribution.** CDP `Profiler` at a 100 µs sampling interval
  over the same gestures.
- **Visual verification.** Screenshots at DPR 2 diffed per pixel against the
  unmodified build, at the opening view, at 3.6× and 4.9× zoom and at
  `MAX_ZOOM`, with Administrative **on** — the harder case, since that is when
  province cracks could show.
- **Sizes.** `gzip -9` and `brotli -q 11` on the real files.

Three caveats, stated plainly:

1. **Software rasterisation** (swiftshader). Absolute milliseconds are not
   comparable with the ~2,490 ms already on record for a real device. The ratios
   are what the harness is for, and they are stable across repetitions, across
   DPR 1/2/3, and at two zoom levels.
2. **The build moved under the audit.** Raster measurements were taken against
   `japan-empire-map.svg` as of 08:30
   (`03d823341b2fa626cfd8e462838940678b120e05`); three commits landed during the
   audit and the file is now
   `18c97e2873bb1114ea7c23d4241fc957a375c0cd`. I re-verified against the current
   file that every structural fact here still holds — `#backings` is still
   1,333 KB / 102,085 vertices / 49.8% of path data, `#seams` still 12.4%, and
   `#backings path` still carries `stroke-width: 1.3` with `non-scaling-stroke`.
   No conclusion depends on the difference. Byte counts in Part 2 are against
   the current file.
3. **No project file was modified.** Verified with `shasum` and `git
   hash-object` against `HEAD`. The only thing this audit added to the
   repository is this file. (`map.js` shows as modified in `git status` — that is
   the atoll/`covers()` work done in parallel during the audit, not mine.)

## Recommendations, ranked by value for effort

### 1. Take the crack-filling strokes to the hairline fast path

**Change.** `styles.css`: `#backings path { stroke-width: 1.3 }` → `1`. Then, if
the diff looks acceptable, `.atom { stroke-width: 1.3 }` → `1`. One character,
then one more.

**Evidence.** RasterTask over the standard drag: **890 ms → 322 ms** for the
backings alone (−64%), **→ 147 ms** for both (−83%). Identical at DPR 1, 2 and
3. It holds when zoomed in: at 5 wheel steps in (`viewBox` 218 units) the
baseline is 177 ms and the backings change is 55 ms, −69%.

**Expected gain.** Against the figure on record, roughly 2,490 ms → 900 ms over
a 1.4 s drag for the one-character version, or → 420 ms for both.

**Risk / cost.** This is the only recommendation with a visible cost, so it must
be looked at rather than taken on the numbers. Per-pixel diffs against the
current build, Administrative **on**:

| view | change | differing > 8/255 | > 40/255 | max Δ |
|---|---|---|---|---|
| opening view | backings → 1.0 | 9,999 (0.76%) | 582 (0.044%) | — |
| opening view | both → 1.0 | 18,979 (1.44%) | 8,071 (0.61%) | 185 |
| 3.6× zoom | backings → 1.0 | 0.49% | 0.091% | 113 |
| **4.9× zoom over eastern China, provinces drawn** | **backings → 1.0** | **2,567 (0.102%)** | **0 (0.000%)** | **27** |
| 4.9× zoom, same frame | both → 1.0 | 6,202 (0.246%) | 10 (0.000%) | 48 |
| `MAX_ZOOM` | backings → 1.0 | 0.43% | 0.29% | 212 |

I rendered the differences amplified six to eight times and looked at them. At
the opening view the change is a single faint line along the **coastlines** and
nowhere else — the outer edge of the land moves by 0.15 device pixels, because
the backing's stroke is what defines the seaward edge. **No interior crack
reopened anywhere**: not in China, not across the Philippines, not in Indochina,
not along the Manchurian or Jiangsu–Zhejiang province boundaries. The deep-zoom
frame over eastern China with the admin layer loaded — the case most at risk,
because with `non-scaling-stroke` the patch is constant in screen pixels while a
crack would grow — has **zero pixels differing by more than 40/255 and a maximum
delta of 27**. A reopened crack would show as a full-contrast line; there is
none.

The remaining uncertainty is at `MAX_ZOOM`, where 0.29% of pixels move
strongly. Worth checking a few known-difficult frontiers by eye before
committing. If 1.0 does prove too narrow somewhere, §8 gets most of the same win
without touching the width at all.

The atoms change is the larger of the two (1.44% at the opening view) for a
further 19 points of raster. Take the backings first; decide the atoms by eye.

**Principles.** Preserves all three. No geometry is simplified, no source
changes, the single-file build is unaffected. It is a rendering change, not a
cartographic one.

### 2. Emit relative path commands

**Change.** `ring_to_path` (`build_map.py:2702`) and `line_to_path` (2726):
relative `l`, implicit lineto, sign elision, deltas accumulated on the printed
grid so rounding cannot drift.

**Evidence and gain.** 817 KB → **451 KB gzipped (−45%)**, 2,850 KB → 1,888 KB
raw (−34%), at bit-identical geometry. Inferred from the load figures on record:
roughly **1.8 s off "map on screen" on slow 4G**. Also 940 KB off the standalone
bundle.

**Risk / cost.** Low, but there are four downstream parsers of the emitted `d`
strings that would break and must be updated together:

- `drop_interior_slivers` (`build_map.py:2440`) — `re.findall(r"-?\d+(?:\.\d+)?", d)`
- the fine-layer bbox pass (`build_map.py:6051`)
- `boxesOf` (`map.js:2945`) — same regex; would have to accumulate deltas
- `reprune` (`map.js:3051`) splits `d` on `'M'` to cut out superseded sub-paths,
  which still works, but the sub-path's first point becomes relative to the
  previous sub-path unless the emitter keeps `M` absolute (it should).

The safe form is: absolute `M` per sub-path, relative `l` within it. Then
`reprune`'s split-on-`M` keeps working unchanged and only the number-scanners
need attention. The build is already verified byte-for-byte against `--legacy`,
so there is a ready-made harness for proving the geometry is unchanged: decode
both encodings back to coordinates and compare.

**Principles.** Preserves all three outright — the geometry is not touched.

### 3. A service worker

**Evidence.** GitHub Pages sends `cache-control: max-age=600` on every asset and
that is not configurable. So there is **no long-term caching at all**: every
visit more than ten minutes after the last one pays six conditional round trips,
and any changed file is re-downloaded whole. `ETag` revalidation means a student
will not get a *stale* map — the cost is the opposite one.

**Gain.** Cache-first on the six boot assets turns a 5.5 s repeat visit into
roughly **0.3 s** (**inferred**). For a classroom tool that students open
repeatedly, in a lab or on a phone in a seminar room, this is worth more than
any byte reduction — and it composes with §2 rather than competing.

**Risk / cost.** Moderate and mostly about discipline: a service worker that
caches aggressively needs a version bump wired into the build, or students see
last week's map with no way to force a refresh. Given the build already computes
content hashes for its seam cache, keying the SW cache on a build stamp is
straightforward. Also: register it only from `https://`, so the `file://`
standalone path is unaffected.

**Principles.** Preserves all three; the offline single file is a separate
artefact and is untouched.

### 4. Two lines that unblock the SVG fetch

**Evidence.** The three scripts are correctly at the end of `<body>`
(`index.html:217–219`) so they do not block first paint (FCP 764–816 ms). But
`map.js:279` issues `fetch('japan-empire-map.svg')` at top level, so the SVG
request cannot start until **all three scripts have downloaded and map.js has
been evaluated**. Measured on slow 4G: the last script lands at 1,202 ms and the
SVG request goes out at 1,210 ms — eight milliseconds later. The SVG spends its
first 1.2 seconds not existing.

`cities-gaz.js` (24 KB gz, 890 records) is part of that chain and **Cities
defaults off**, so none of it is needed to show the map.

**Change and gain.** Both measured as A/B against the live site:

- `<link rel="preload" href="japan-empire-map.svg" as="fetch" crossorigin>` in
  `<head>`: SVG request moves 1,214 ms → ~187 ms, map-ready **5,538 → 5,210 ms
  (−328 ms)**. It needs `as="fetch"` *and* `crossorigin` or it downloads twice.
- Loading `cities-gaz.js` on demand instead of at boot: map-ready **5,538 →
  5,227 ms (−311 ms)**, FCP 774 → 640 ms.

Roughly **0.6 s for two lines**, and it composes with §2.

**Risk / cost.** The preload is free. Deferring `cities-gaz.js` needs a guard
wherever `JMAP.GAZ` is read before it arrives — the same shape as the existing
`loadAdmin` race that `map.js:384–390` already documents having got wrong once,
so the pattern to copy is right there.

**Principles.** Preserves all three, but note the standalone build inlines
everything, so the deferred fetch needs the same `JMAP_INLINE_*` guard the other
lazy files have (see §11).

### 5. Stop `getBoundingClientRect` running per province per mousemove

**Evidence.** CDP profile of 51 mousemoves across China at 4× throttle,
Administrative on: **`getBoundingClientRect` is 91.8 ms of self time — 61% of
all JS in the sweep**, 1.8 ms per pointer event. With Administrative off it is
still 77.1 ms. Next largest are `getBBox` at 12.4 ms and `showTooltip` at
6.4 ms; `onHover` and `pick` together are 4.5 ms. The timeline agrees: 136 ms of
forced synchronous `Layout` across the sweep with Administrative on, 100 ms
without.

The source is `nearestSubUnit` (`map.js:1735–1759`), which does
`$$('[data-prov]', atomEl)` and then calls `getBoundingClientRect()` on every
result — several hundred rects inside British India, each a forced layout flush,
on every mousemove. `showTooltip` (`map.js:2137`) adds a write-read-write per
event: `innerHTML` at 2140, rect read at 2213, style write at 2217.

**Change.** The build already emits `data-cx`, `data-cy`, `data-area` and
`data-hits` per atom. Emit `data-bbox` per `[data-prov]` path the same way and
let `nearestSubUnit` do the arithmetic in user space against the current `view`,
which it already has — no layout read at all. Cache the tooltip's measured size
and re-measure only when its content changes.

**Gain.** Removes ~60% of hover JS and essentially all forced layout on the
hover path: about 3.3 ms → 1.3 ms per pointer event at 4× throttle. Desktop only
(the handler is behind `hoverCapable`), which is why it sits below the pan and
load work.

**Risk / cost.** Contained: one added build attribute, one function rewritten.
Worth a check that the new nearest-sub-unit answer matches the old one over a
grid of sample points before switching.

**Principles.** Preserves all three.

### 6. Take the prose and the unused epoch off the critical path

**Evidence.** Of the 977 KB gzipped initial payload, about **65 KB (6.7%) is
dead weight at first paint**:

- **250 `note:` strings in `data.js`: 51,234 raw bytes, 29.3% of the file**, read
  only when a place is clicked. Stripping them takes `data.js` from 62,356 to
  41,316 gzipped — **−21 KB gz (−34%)**.
- **Both epochs ship while one is displayed.** `cities-gaz.js` is a 50/50 split
  (47,936 / 47,653 bytes) and **238 records are byte-for-byte identical between
  them — 25% of the file**; all 444 of the 1930 ids reappear in 1942. In
  `data.js`, TERRITORIES is 31,987 (e1930) + 37,475 (e1942) plus per-epoch
  CATEGORIES, PROVINCE_EPOCH, CLUSTER_EPOCH and EPOCH_OVERRIDES. ~13 KB gz
  unused at boot.
- **Repeated literal keys**: 21,283 B (12.1%) of `data.js`, and **25,082 B
  (26.2%) of `cities-gaz.js`** — one byte in four. A columnar layout
  (`[id, n, lat, lon, t, c, p, of]` with a header row) removes nearly all of it.

**Gain.** ~45 KB gz, roughly 225 ms on slow 4G, and it makes §4's deferral of
`cities-gaz.js` cheaper because there is less to defer.

**Risk / cost.** Low. The notes move to a `notes.json` fetched on first
selection; a shared base plus per-epoch deltas for the gazetteer is a build
change with an obvious equality check (round-trip and compare).

**Principles.** Preserves all three, again with the standalone-inline caveat.

### 7. The cheap `map.js` fixes

- **`applyView` forces a layout flush on every raw pointer event.**
  `map.js:1215` writes the `viewBox`; `map.js:1218` immediately calls
  `defaultView()` → `activeBounds()`, which calls `getBBox()` on all 55 atoms
  plus two or three `getBoundingClientRect()`s. Write-then-read, per event, not
  per frame — and all of it exists to set two classes (`zoomed-in`, and the reset
  button's `idle`) that depend only on `view.w`, which does not change during a
  pan. Guard the block on `view.w` having changed and cache `defaultView()`
  until the container resizes. Measured cost in the pan profile is small
  (`getBBox` 2.1 ms, `getBoundingClientRect` 1.8 ms over the whole drag) — this
  is removing a per-event forced layout on principle, not a headline win.
- **`onResize` is wired to `visualViewport.resize` (`map.js:409`) with no
  debounce**, and each call runs `applyView(true)` → `rescale()`, which writes
  transforms to ~1,550 elements. On iOS that event fires continuously during
  keyboard show/hide and pinch. rAF-coalesce it.
- **`redrawHighlight` runs on every `setHotProv` change, not just `setHot`**
  (`map.js:2433`, called from 2060). Crossing from one province to the next
  rebuilds the whole *country* silhouette — for occupied China that is reading
  752 `d` attributes, concatenating them, and writing the result twice (mask
  solid and masked stroke), plus a fresh `<mask>` and possibly a fresh
  `<clipPath>`. Memoise on `(hot, hotProv, selected)` and skip the territory
  silhouette when only `hotProv` moved.
- **`boxesOf` regex-tokenises every `d` in `#land` on every fine graft or drop**
  (`map.js:2945`, from `reprune` at 3013/3076/3097/3121) — including the 307 KB,
  233 KB and 205 KB paths, ~1,500 nodes per sweep. Debounced to 220 ms so it is
  not per frame, but it fires on every settle that crosses a window boundary and
  then runs `buildHatch`, `applyState` and `redrawHighlight` behind it. Cache
  the boxes per node keyed on the `d` string; `coarseOrig` already gives a
  stable key.
- **`clip-china` is 233 KB of geometry that already exists elsewhere in the same
  file** (`build_map.py:5069–5076`) — a verbatim concatenation of China's 21
  province paths and its 103 KB backing. It costs nothing at raster time (Part 1)
  but it is 233 KB of transfer, parse and DOM. A `<clipPath>` containing a
  `<use href="#…">` of the backing removes most of it.
- **The fine layer's 101 largest islands are emitted at one decimal place with a
  0.05-unit dedupe** — coarser than the 0.04-unit tolerance they were just
  simplified at — for 177 KB of the fine file's 374 KB (`build_map.py:6019`,
  `ring_to_path` called with `precision=None`). They are only ever shown at deep
  zoom, where 0.1 units is 4–10 screen pixels, so this is quantisation that
  shows up exactly where the layer exists in order not to. Pass
  `FINE_PRECISION` explicitly.
- **`fineDoc` retains ~1.1 MB for the session to serve 24 KB.** It is a
  module-level `var` (`map.js:2882`) assigned in `fetchFine`'s parse (2983) and
  never nulled. Measured: holding the parsed fine document costs 1,106,214 bytes
  and 2,007 nodes, and a nine-step zoom onto the Ryukyus grafts 126 paths /
  24,480 bytes out of it — **46:1**. Keep the `g[data-for]` fragments actually in
  use and drop the document, or re-fetch from HTTP cache on the rare regraft.
  (`adminDoc`/`rocDoc` are correctly written as locals and do become garbage;
  `provSets.enp` + `provSets.roc` intentionally retain 1.86 MB of `d` strings if
  a student ever touches the AMS-1936 radio, which is defensible for instant
  toggling but worth knowing.)
- **Administrative "off" frees nothing.** SVG element count and `d=` bytes are
  byte-identical between off and back-on (6,311 / 1,373 / 3,945,397): the toggle
  is CSS visibility only, and once the 1.17 MB of province geometry is grafted it
  stays for the session. Correct as a responsiveness decision; worth stating.
- **A LayoutObjects leak across an epoch round trip**: 6,167 → 7,870 at 1942 →
  6,821 back at 1930. 654 layout objects (+10.6%) that did not exist before.
  Worth a look at the 1942-only layer teardown.
- **`index.html:25–27` ship all three layer buttons as `class="on"
  aria-pressed="true"`** while the JS default is all-false, so they render
  pressed from FCP (~780 ms) until `applyState()` runs (~1,210 ms) — 430 ms of
  wrong state, and wrong `aria-pressed` for anything reading early.

### 8. Pan by compositor transform over a pre-painted margin

This is the architectural answer to "nothing is composited". It works, but not
in the naive form, and it is the one item I would want prototyped behind a flag
and measured on a real phone.

**What was tested**, in increasing order of honesty:

- `will-change: transform` added, still rewriting `viewBox`: **847 ms, no
  change**. Promotion alone buys nothing, because a `viewBox` rewrite
  invalidates the layer's contents completely.
- Hold the committed `viewBox` during a drag and move the `<svg>` with a promoted
  CSS `translate`, committing on release: **RasterTask ~0 ms after the first
  frame** (71, 0, 0, 0 across four repetitions). But it is visually wrong — I
  screenshotted mid-drag and there is an unpainted band down the right edge and
  along the bottom, because the element has simply moved off its own painted
  area.
- The same thing **over a pre-painted margin**: `#map-svg` inset by one viewport
  on each side, `viewBox` enlarged by the same proportion so the scale is
  unchanged, `#map-container` clipping, and a re-commit when the drag runs past
  the margin or on release. Mid-drag screenshot is **correct, full coverage to
  every edge**. RasterTask **101 ms**, combined with §1. With half a viewport of
  margin instead of a full one it is 330 ms — Chrome paints the layer's tiles
  lazily, so a translation that brings unpainted tiles into view still costs, and
  the margin width matters.

**Gain.** 890 ms → 101 ms, **−89%**, the best of anything measured. It also
subsumes §1's mechanism during a drag: the SVG's internal CTM stops changing, so
`non-scaling-stroke` stops re-tessellating.

**Risk / cost.** The highest here, which is why it is eighth and not first.

- Every screen-space calculation in `map.js` that assumes the `<svg>` box is the
  viewport box has to learn about the margin: `containerSize`, `clampView`,
  `fitView`, `viewForBox`, `zoomAt`, `focusOn`, `uiBoxes`, `keepClear`,
  `placeLabels`, `reachable`, and the pointer-to-user-space conversion in
  `pick`. That is a wide blast radius through the most load-bearing part of the
  file.
- Painting three viewports in each axis is 9× the pixels per commit. One commit
  per gesture instead of fourteen frames is still a large net win, but a zoom
  gesture commits on every wheel tick unless zoom is handled separately.
- Compositing memory: at 390×844 and DPR 2 the promoted layer with a
  one-viewport margin is about **45 MB of backing store** (**inferred** from
  1.23 Mpx × 9 × 4 bytes; the un-margined layer measured 1.23 Mpx / 5 MB, and I
  could not read GPU memory directly from this harness). On a low-memory phone
  that is a real number and must be measured on a device. A 0.5 margin costs 4×
  rather than 9× and measured 330 ms — a reasonable middle setting.

**Sequencing.** §1 gets 64–83% for two characters. This gets 89% for a week of
careful work. Do §1 regardless; do this only if §1 proves insufficient, and if
it is done, §1's width change becomes optional rather than necessary.

**Principles.** Preserves all three; it is purely a rendering strategy.

### 9. Tier the geometry by zoom, if the payload still needs to come down

Only reach for this after §2, and frame it carefully, because it is the one
recommendation that engages *never simplify geometry unasked*.

**Evidence.** The geometry is oversampled for the screen at every zoom the map
allows, and unevenly so. One unit is 0.05° ≈ 5.57 km; the opening view on a
phone is 785.4 units in 390 CSS px, so **one unit is 0.497 CSS px**. Across
204,066 vertices:

| segment length | ~0 (exact duplicates) | ~0.01 u | ~0.1 u | ~1 u | ~10 u | >100 u |
|---|---|---|---|---|---|---|
| count | 6,488 | 13,426 | 74,310 | 97,548 | 7,826 | 107 |

At the opening view, 74,310 vertices describe steps of about 0.05 CSS px and
19,914 describe steps of 0.005 CSS px or less.

And the density is inconsistent. **`FULL_DETAIL` (`build_map.py:561`) exempts
China, Manchuria, Tibet, Xinjiang, Chahar, Suiyuan, Jehol, Korea, Malaya,
Manchukuo and Mengjiang from simplification entirely**, while every neighbour
they touch has been through Douglas-Peucker at 0.55 units (≈ 3.1 km). The map
already accepts 3.1 km of deviation on Siam and the USSR while carrying raw
source vertices on China.

Douglas-Peucker at 0.1 units — **five times finer than what the rest of the map
already gets** — moves **six pixels out of 1.3 million at the opening view** and
takes 17% off pan raster. At `MAX_ZOOM` it moves 0.14%, so a single global
tolerance is the wrong shape.

**Change.** Two parts.

(a) **Apply 0.1–0.2 units to the `FULL_DETAIL` set alone.** Those shapes would
still be the most detailed geometry in the file — more detailed than every
neighbour they touch — and that is where most of the bytes are. This is a
narrow, defensible first step.

(b) **Tier by zoom, exactly as the fine coastlines already are.** Ship the base
at ~0.15–0.2 units and swap the full-detail geometry in for the region in view
once the reader is close enough for it to matter. `FINE_W = 150` is already the
threshold where the map admits Natural Earth "starts to read as a polygon";
`syncFine` already grafts and ungrafts per-window geometry on a 220 ms debounce;
`data-fine` already carries the window boxes; `coarseOrig` already stashes what
was replaced. The mechanism exists and is proven — this would be a second client
of it.

Related and measured: **43.6% of all path data (184 paths, 1,215,228 bytes ≈
356 KB gz) is entirely outside the opening viewport** — British India, the
western Pacific, the far south. Splitting the file at the viewport rather than by
tolerance is a second, independent axis worth about 1.8 s on slow 4G, and it does
not simplify anything at all.

**Principles.** (a) and the viewport split preserve all three. (b) needs the
argument stated rather than assumed: the principle is *never simplify geometry
unasked*, and a zoom-tiered scheme does not simplify what the reader is looking
at — it defers detail that is provably below the pixel grid at the current zoom
and delivers it in full the moment it would become visible, which is what the
fine layer already does from the other direction. What would violate the
principle is shipping 0.2 units as the only geometry there is. The standalone
build must carry the full-detail geometry regardless, since it has no network.

### 10. Host somewhere that serves brotli

**Evidence.** Measured with `curl -H 'Accept-Encoding: gzip, br'`: GitHub Pages
gzips `.svg` (good, and sets `Vary: Accept-Encoding`) but **never offers
brotli**, even when `br` is first. For the current SVG that is 817 KB gzip
against **442 KB brotli**; for the relative-encoded SVG from §2 it is 451 KB
against **329 KB**.

**Gain.** −375 KB / ~1.8 s on slow 4G today, or a further −122 KB on top of §2,
for **zero code change** — Cloudflare Pages and Netlify both do it.

**Risk / cost.** A hosting move, not a code change. Weigh it against giving up
GitHub Pages' zero-maintenance story for a teaching tool; it composes with §2
and §3 rather than competing, so it can wait.

### 11. Two correctness bugs in the offline story

Not performance, but they were found while measuring it and they defeat a stated
principle.

- **`japan-empire-map-standalone.html` is stale.** The inlined coarse SVG is
  2,592,302 bytes; the current `japan-empire-map.svg` is 2,849,634. The bundle is
  dated 13 August; `map.js`, `data.js` and all four SVGs were regenerated on the
  17th. Anyone handed the standalone file gets a four-day-old map with an old
  `map.js` and `data.js`. Nothing regenerates it — `tools/bundle.py` is not
  wired to `tools/build_map.py` and there is no CI. **Wire the bundle into the
  build.**
- **The single file does not work fully offline.** `bundle.py` inlines `svg`,
  `admin` and `fine` but **never `japan-empire-map-roc.svg`**, and `loadRoc()`
  (`map.js:3204`) has **no `JMAP_INLINE_ROC` branch**, unlike the other three
  (`map.js:276`, `2987`, `3271`). So selecting "AMS 1:250,000, 1936" in the
  standalone build fires a `fetch` that fails from `file://`, hits the `.catch`
  at `map.js:3226`, resets the radio to ENP and swallows the failure silently.
  The feature is invisibly dead offline. Adding it costs +245 KB gz to the
  bundle — or +146 KB after §2.

Also worth noting, though it costs the student nothing: **146.9 MB in 116 tracked
files is published to Pages**, of which about 1 MB is needed —
`occupation-maps/*.jpg` (up to 14.7 MB each), `tools/cache/admin0.geojson`
(13.3 MB), `tools/cache/rivers.geojson` (7.3 MB), plus `tasks.md`, `rr.html` and
now `reports/`. That is 150× the size of the thing being delivered, all publicly
served, against GitHub's 1 GB soft limit for a Pages site.

## Negative results

Things that look like the answer and are not. Each cost real time to rule out.

- **`#seams` is 12.4% of all path data and removing it changes pan raster not at
  all** (901 ms vs 890 ms). Fill-only with `stroke: none`, so it never enters
  stroke tessellation. Its cost is bytes, not frames.
- **Removing both `clip-path` attributes changes nothing** (907 ms), despite
  `clip-china` being 16,368 vertices — the kind of thing that usually is a
  raster cost here and is not.
- **`will-change: transform` on its own is worthless** (847 ms) while the
  `viewBox` is still being rewritten. It pays only in combination with §8.
- **Dropping the 6,488 exact duplicate vertices gives no measurable raster gain**
  (960 ms, within noise). Do it for the bytes and the bug, not the frames.
- **`applyGazetteer`'s 890 `style.display` writes per rAF frame and
  `placeLabels` running every frame do not show up at all** in the pan profile —
  the entire JS cost of a drag is `getBBox` 2.1 ms, `getBoundingClientRect`
  1.8 ms, `onPointerMove` 1.6 ms. They are O(n) per frame and alarming in the
  source, but writing a `style.display` that already holds that value is close to
  free. Not worth changing for performance. This independently confirms the
  existing finding that pan JS is 41–82 ms and not the problem.
- **Scale-compensating the strokes with `calc(1.3 * var(--vk))`, updating `--vk`
  only when the zoom changes, did not work** (858 ms). Nor did hard-coding the
  same widths as literal constants (855 ms). Both leave the stroke above 1 unit
  in the units Skia checks, so both stay off the hairline path. **The width is
  what matters, not how the width is expressed.**
- **The 2.7 MB `svgHost.innerHTML = markup` is a non-issue: 58.7 ms at 4× CPU
  throttle** (~15 ms on a real phone), because the file is only 6,043 elements —
  the bytes are inside a handful of enormous attribute values, and attribute
  scanning is nearly free next to element construction. `DOMParser` on the same
  string is 56.7 ms. **Do not restructure the boot around this.**
- **`ParseAuthorStyleSheet` for the 45 KB stylesheet is 0.9 ms.** Script
  evaluation for all four scripts is 18.6 ms. Total main-thread CPU for the
  entire boot is ~400 ms at 4× throttle, i.e. ~100 ms unthrottled.
- **Script placement is already correct.** Adding `defer` measured no benefit
  beyond the preload in §4 (5,198 vs 5,210 ms).
- **JS heap is a red herring for memory**: 2.6 MB at boot for a 2.85 MB SVG,
  because the geometry lives in the renderer's attribute arena, not in V8. The
  honest measure is total `d=` bytes: 2.79 MB at boot, 4.09 MB after
  Administrative + fine + 1942.

The through-line: **on the load side every meaningful win is a byte, not a
millisecond of CPU. On the raster side every meaningful win is a stroke or an
encoding, not a vertex.**
