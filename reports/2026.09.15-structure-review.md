# The shape of the JavaScript, reviewed

**Date:** 15 September 2026.
**Subject:** how messy, disorganized and convoluted the JavaScript has become,
and what to do about it without a rewrite.

## Method

Measured rather than eyeballed. Every figure below comes from a script run
against the working tree; where something is an estimate it says so.

* Sections of `map.js` taken from its own `/* ----` banner comments, with the
  line span between each banner and the next.
* Function lengths from a brace-depth scan over the comment- and
  string-stripped source, so a function's length is its code, not its prose.
* Module-level state counted at the closure's own indentation.
* Dead code by listing every declared name and grepping for a call or
  reference elsewhere, then confirming each survivor by hand.
* CSS selectors extracted from `deploy/styles.css` and matched against
  `deploy/index.html` and every hand-written script.
* Comments are **not** counted as mess; this project's rule is that they
  argue at length, and they do.
* The test runner's section selection was checked by re-implementing
  `mapSections()` (`tools/test/all.js:345`) verbatim — the same banner regex,
  the same `MAP_SECTIONS` table — and running it over the file, rather than by
  editing `map.js` to provoke a diff. Nothing in the repository was modified
  except this file.

*Caveat on the tree.* Another session was editing `trains.js` and
`deploy/index.html` while this ran. The `map.js` figures — which is nearly all
of the above — are for `c46edd8` untouched; the `trains.js` line and `var`
counts are for the working tree as it stood when they were taken.

## The short version

`map.js` is 21,182 lines — up 3,217 (18%) since 9 September — still one IIFE,
now holding **382 module-level variables** (319 six days ago) and 571
top-level functions. The code inside remains sound; the mess is structural
and it is getting worse at a measurable rate, about 500 lines and 10 module
variables a day.

Four specific faults, in order of how much they cost:

1. **The test runner's section map is broken, and the file's shape is why.**
   `MAP_SECTIONS` (`tools/test/all.js:328`) picks test groups from the banner
   above a changed line. Four banners its regex cannot see, and five banners
   that no longer describe what follows them, mean an edit to the rail menu
   never runs `transport`, an edit to a population table never runs `data`,
   and an edit to the relief fetch never runs `geometry`. §1.2a.
2. **The section banners no longer describe the sections.** The worst is
   `the right-click menu` (`map.js:13427`): a 209-line subject whose banner
   covers **1,713 lines** holding seven others, including the whole population
   table subsystem and both card renderers.
3. **The air subsystem is in five disjoint pieces** across 5,500 lines, though
   it has its own data, card, menu, host function and an already-lazy player.
   It is the split the 9 September review named and did not do, and it has
   grown since.
4. **`wireControls`** (`map.js:19704`) is 752 code lines, 71 listeners and one
   `var` scope — the largest function in the repository by a factor of three.

The call graph over `map.js` has **72 cycles**. That number is the headline:
there is no direction of flow in this file to follow.

### 1.2a Four banners the test runner cannot see

This is not cosmetic. `MAP_SECTIONS` (`tools/test/all.js:328`) decides which
test groups a `map.js` edit runs, keyed on the banner above the changed line.
A banner its regex misses hands its lines to the section above:

| invisible banner | why | falls into | groups run | groups that should run |
| --- | --- | --- | --- | --- |
| `the six railways, one by one` `map.js:16529` | opens with four dashes, not six | `the sheets, on a menu` | `core`, `data` | `transport` too — it holds the rail, station and train menus |
| `shaded relief` `map.js:1901` | no trailing dashes; the title ends the line | `projection` | `core` | `geometry` |
| `THEMATIC LAYERS` `map.js:8647` | the title is on the *next* line | `hit testing` | `core` | `core`, `data` |
| `the keyboard` `map.js:20698` | indented four spaces, not two | `controls` | `core`, `links` | (harmless) |

So **an edit to the rail, station or train menu (`map.js:16563`, `16836`,
`16925`) never runs the `transport` group**, and an edit to the relief fetch
and fade (`map.js:1945–2139`) never runs `geometry` — even though
`MAP_SECTIONS` carries a rule mapping `shaded relief` to `geometry`, which can
therefore never fire. Two further banners, `Japan's railways` (2166) and
`applying state` (15140), are seen but have no rule, so they correctly fall
back to the whole suite — which is why edits to `railFade` itself are still
covered.

The mislabelled sections misroute too: an edit to `popTableFor`
(`map.js:14512`) sits under `the right-click menu`, mapped to `points`,
`core`, so the **`data` group - `population`, `demography`, `japanpop` - is
not run**. An edit to `drawRelief` (`map.js:3436`) sits under `train tools`,
mapped to `transport`, so `geometry` is not run.

## 5. A reorganisation plan that needs no rewrite

The mechanism already exists and is proved four times: `loadScript(name)`
(`map.js:64`) returns a memoised promise; a `*Host()` function hands the
module the dozen things it needs; the module keeps its own state and exposes a
small API. `annHost` has 18 members, `trainHost` 18, `airHost` 9. Nothing
below invents anything.

For each candidate: the code lines it would take with it, the module-level
variables that would move *with* it (referenced at most once outside), and the
variables that would have to be passed through a host (referenced more than
once outside). Measured, not estimated.
